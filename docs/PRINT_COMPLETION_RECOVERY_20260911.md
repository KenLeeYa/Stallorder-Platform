# 重印成功後的訂單完成復原

2026-09-11，正式店員看板發生：第一張工作列印失敗／取消，印表機重啟後重印成功，但已付款訂單仍顯示「列印需要處理」，無法完成。

## 根因與修正範圍

看板資料與完成訂單 API 都只讀最早的原始工作，排除所有 reprint。實際成功的重印未反映到訂單的 primaryPrintStatus。當訂單仍是 CONFIRMED，自動列印完成回呼也不會將其結單，因此操作路徑一直被舊失敗狀態阻擋。

共用狀態計算保留最早主工作的定義，包含同文件類型、非分流副本的所有後續重印。任一次已回報成功即可完成列印需求；尚未成功時顯示最新重印狀態。原始及重印的歷史紀錄、payload 與實際列印結果不改寫。其他收據、分流副本與其重印不算主票成功。

使用此計算的三個位置：

1. Staff 訂單讀取與序列化，讓平板三欄和手機卡片恢復完成操作。
2. 完成訂單 API，避免畫面可按但後端仍等待舊工作，不額外排印或收款。
3. 列印成功回呼，只有主票完成且已付款 READY 的合格櫃檯單能自動結單；CONFIRMED、未付款、QR、KDS 或外部平台訂單仍保留原本限制。

不涉及 migration、Edge、印表機設定、憑證或自動出單規則變更。事故期間經店主確認紙張完整印出，另以資料庫既有成功重印紀錄對受影響單筆主工作進行有稽核的狀態校正；未代為完成訂單、改款項或品項。此一次性復原不取代通用程式修正，實際復原 SQL 與回讀保存在本機事故證據目錄，未放入客戶資料或秘密到版本庫。

## 驗證

- 先以真實狀態組合建立失敗測試：CANCELLED 原始票 + SUCCEEDED 重印，在舊版仍序列化為 CANCELLED；修正後為 SUCCEEDED，訂單仍 CONFIRMED/PAID。
- 單元測試：一次及多層重印、待列印／列印中／失敗／取消、其他收據、分流與分流重印、後續備份票失敗、時間相同的排序、QR/付款/KDS/狀態限制、重複完成回呼。
- Playwright：原始票取消 → 第一次重印失敗取消 → 再次重印成功 → 平板與手機均恢復完成按鈕 → 完成 API 成功 → 無重複扣款、無新增列印、歷史保留；重複成功回呼及重複完成均拒絕。
- 發布前須通過全套單元、型別、lint、build、CI/Preview 及既有 QR/KDS 流程。正式發布仍由新 Staging/main tree 的 Application Plan/Apply 與線上 smoke 證明；本文件不是發布成功宣告。
- 本機測試服務按需啟用，測試後停止；保留資料。自動化回呼模擬不代替 iPad/印表機實機驗證。

首輪 CI `34563371241` 在新案例準備階段由 `orders_checkout_amounts_check` 擋下：模擬訂單從外帶改為內用時漏了必填桌號。已補齊合成桌號 `QA-A1`，保留資料庫限制及全部重印／完成／付款斷言，重新執行同一完整驗證；該失敗發生在開始瀏覽器操作前，不能當作此流程已通過。

保留資料的本機環境有多個測試組織，新增案例改用既有的登入 helper，再明確進入指定攤位，避免假設登入後一定直接進看板。2026-09-11 本機完整重印復原案例已通過（Chromium，1024×768 與 390×844），包含 API、畫面、歷史及重複操作的全部斷言；測試中 409 為預期的重複操作拒絕。
