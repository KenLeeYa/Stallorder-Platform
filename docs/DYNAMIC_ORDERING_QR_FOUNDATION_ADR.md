# ADR: Dynamic Ordering QR Foundation

- Status: Local foundation only; Production rollout not approved
- Date: 2026-08-13
- Scope: Short-lived dine-in ordering credentials backed by an existing printed QR and canonical order session

## Context

Square documents a durable QR ordering model in which printed QR codes are assigned to ordering stations such as a table, seat, or parking spot. Merchants can stop accepting QR orders and later turn acceptance back on; the printed station QR remains the entry point. StallOrder keeps that model as the baseline and adds an optional short-lived credential only as defense in depth for high-risk dine-in service points.

The dynamic credential is not a new menu, tenant, table, session, checkout, or order authority. A JavaScript failure, invalid credential, expired capability, emergency pause, or rotation must direct the guest to a safe instruction to scan the printed static QR. This foundation deliberately adds no customer UI or public handler.

Reference: [Square, Set up and manage QR code ordering for your website](https://squareup.com/help/us/en/article/7142-set-up-self-serve-ordering-and-qr-codes-with-square-online).

## Decision

1. `DYNAMIC_ORDERING_QR_FOUNDATION_ENABLED` is inserted with `default_enabled=false` and `is_emergency=false`. It is a rollout gate, not an emergency override. Runtime emergency controls are the service-point `PAUSED` state and credential rotation.
2. Every service point is one active `dining_table` plus its existing printed `qr_codes` row. Configuration starts `PAUSED`; activation is an explicit service-role operation. The migration never changes, pauses, rotates, expires, or deletes the static QR.
3. Issuance accepts high-entropy token and nonce hashes generated by trusted server code. Raw credential material is returned only by the server module and is never persisted. Stored scope is immutable: organization, stall, table, static QR, canonical order session, device hash, credential version, expiry, and usage limit.
4. Credentials expire in 60–900 seconds and allow 1–3 redemptions. Current safe defaults are 300 seconds and one redemption. A row can only move from `ACTIVE` to a terminal or invalidating state: `CONSUMED`, `PAUSED`, `ROTATED`, `CHECKED_OUT`, `EXPIRED`, or `REVOKED`.
5. Redemption serializes on the service point and credential, checks both per-credential and per-device rate limits, then verifies flag, version, state, expiry, nonce, device, static QR, table, organization, stall, and existing order session. A screenshot opened from a different device hash fails closed. A moved table, wrong table QR, expired/closed session, pause, rotation, checkout, or replay also fails closed.
6. Dynamic credentials cannot mint a broader scope or a new order session. Successful redemption still calls `public.public_order_preflight` with the existing static QR and existing order-session hash. Order creation remains owned by the existing canonical transaction RPC.
7. Both tables use forced RLS. Direct credential mutation is not granted even to `service_role`; trusted SECURITY DEFINER RPCs are the mutation surface. Tenant-scoped audit stores IDs and reason codes, never raw tokens/nonces or their hashes.
8. All failure responses include a transport-neutral fallback contract:

```json
{
  "kind": "STATIC_QR_RECOVERY",
  "safe": true,
  "static_qr_remains_valid": true,
  "message_code": "SCAN_PRINTED_STATIC_QR",
  "reason_code": "DYNAMIC_QR_*"
}
```

This is the no-JavaScript and credential-failure contract for a later UI/handler phase. It does not expose a URL or raw static token.

## Security properties

- Replay: an exhausted one-use credential is `CONSUMED`; later redemption returns `DYNAMIC_QR_ALREADY_USED`.
- Screenshot sharing: device-hash mismatch returns `DYNAMIC_QR_DEVICE_MISMATCH` without consuming the capability.
- Wrong or moved table: stored table/static QR/session scope must still match current database relationships.
- Expiry: both credential and canonical session expiry are enforced.
- Checkout: trusted checkout invalidation moves active credentials to `CHECKED_OUT`; redemption also detects a consumed or order-bound session.
- Emergency: pause invalidates current active credentials immediately; rotate advances the service-point version and invalidates earlier active versions.
- Fail closed: unknown credentials, malformed values, missing scope, disabled rollout, or unavailable persistence never fall through to ordering.

## Merchant approvals required before Production

Production remains blocked until the merchant approves:

- which physical service points/tables may enable dynamic credentials;
- credential lifetime within the enforced 60–900 second range;
- one-use versus limited-use policy, up to three redemptions;
- strict device binding policy and the support procedure for device replacement;
- who may activate, pause, rotate, and mark checkout invalidation;
- printed static QR placement and fallback wording at every enabled service point.

## Gates

- Local gate: migration reset, pgTAP, static migration contracts, server unit tests, lint, typecheck, and owned diff must pass.
- Production gate: FAIL until the merchant approvals above, handler/UI integration, operational alerting/runbook, Staging rollout with real table scans, and a verified rollback drill are complete.
