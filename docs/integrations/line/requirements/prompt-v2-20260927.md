# QIDAIGO／攤點通：平台單一 LINE 官方帳號整合
## Codex 完整執行提示詞 v2.0

- 編製日期：2026-09-27（Asia/Taipei）。
- 對象：目前開啟的 QIDAIGO／攤點通／Stallorder 原始碼專案。
- 目標：平台 LINE 會員＋攤點通 MINI App＋各店 LINE Pay＋平台官方帳號訂單卡片／取餐 QR／餐點完成及取餐完成通知。
- 版本關係：本檔是可獨立使用的完整版本，取代 v1 的「商家 OA 發訊／店家自行選擇通知聊天室」設計；不必再合併 v1。既有程式已完成的能力要沿用，不因文件改版重做。
- 重要澄清：本檔是需求與工程驗收規格，不是已完成串接、已通過 LINE 認證或已審查原始碼的證明。路由、資料表、事件及設定名稱均須映射 repo 實際實作。

> **不可偏離的核心：顧客在不同合作店家點餐，訂單與取餐通知都集中出現在「攤點通平台」同一個 LINE 官方帳號聊天室。不是各店各發，也不是「LINE MINI App 通知」聊天室。**

## 1. 指定商業模式、參考畫面與目標體驗

### 1.1 三種責任分開

| 責任 | 本版唯一指定模式 |
|---|---|
| 顧客會員 | 攤點通平台顧客會員，使用 LINE 經驗證身分識別 |
| 通知寄件帳號 | 攤點通平台的單一 LINE 官方帳號；合作店家不持有其 Token |
| 商品、接單、製作與交付 | 各合作店家既有後台／POS／KDS，依權限操作自己的訂單 |
| 餐費收款 | 該訂單實際店家的 LINE Pay 商家帳號，非平台統收後分帳 |
| 訂單資料可見性 | 顧客可看自己的跨店訂單；商家只看自己店的資料；平台支援需受控授權與稽核 |

平台統一發通知，不代表所有商家共用顧客名單、不代表平台可任意代收，也不代表 LINE 認證已取得。

### 1.2 參考截圖的可見需求

使用者提供 dudoo「肚肚找美食」的桌面及手機 LINE 截圖。只以可見體驗作需求來源：

- 同一平台 OA 聊天室有訂單金額、取餐 QR、訂單詳情與聯絡店家入口。
- 店家餐點完成後，聊天室出現「餐點已完成，請取餐」訊息。
- 完成交付後，聊天室另出現「已完成取餐」訊息。
- 圖文選單可進入點餐、點餐紀錄等平台服務。

截圖不能證明對方的 API、資料庫、付款收單模式或 QR 安全設計；本版技術方案是攤點通自己的實作規格。不得複製 dudoo 吉祥物、品牌圖案、認證盾牌、顧客姓名或真實 QR。測試用合成資料，不能掃描或呼叫圖片中的真實訂單。

### 1.3 必須成立的完整流程

```text
攤點通平台 LINE 官方帳號，或合作店家 QR／公開點餐連結
  → 攤點通 MINI App：LINE 授權登入
  → 首次確認平台會員條款，建立／連結平台顧客會員
  → 自願加入「攤點通」OA，顯示交易通知可用狀態
  → 選合作店家，沿用菜單、購物車、取餐時間與結帳
  → 顧客向該店的 LINE Pay 商家帳號付款
  → 後端驗證付款及訂單成立條件
  → 攤點通 OA：訂單卡片＋取餐 QR＋訂單詳情／聯絡店家
  → 店員在原後台／POS／KDS 按「製作完成／通知取餐」
  → 攤點通 OA：「某店某號訂單餐點已完成，請取餐」
  → 顧客出示 QR，店員掃描、確認餐點並實際交付
  → 後端唯一一次核銷，更新已取餐／履約完成
  → 攤點通 OA：「某店某號訂單已完成取餐」
```

現金／其他既有支付按原規則仍可使用相同履約通知。尚未付款的現金單，卡片必須如實寫待現場付款；不能為了共用模板寫成 LINE Pay 已付款。

### 1.4 不可違反的不變量

```text
一個平台官方帳號，服務多家合作店；訊息清楚標明實際店家。
一套訂單與履約真相；不另造 LINE 專用訂單資料庫。
LINE 登入 ≠ 已加入好友 ≠ 已同意會員條款 ≠ 行銷同意。
平台顧客會員 ≠ Organization／Stall 員工或管理者身分。
已付款 ≠ 已接單 ≠ 餐點完成 ≠ 已取餐。
通知與取餐 QR 不授予付款、退款、後台或其他顧客資料權限。
同一事件可恢復重試，但不能造成重複扣款、核銷、計費或無限制推播。
LINE API 接受 ≠ 顧客已送達／已讀；不虛構逐則已讀證據。
關閉 MINI App 或 LINE 前景，不影響後端處理可取餐通知。
本檔交付 ≠ 程式已完成 ≠ 實機測試通過 ≠ 官方認證通過 ≠ 已正式啟用。
```

## 2. 官方規格基線與實作前再核對

本版於 2026-09-27 核對關鍵 LINE／LINE Pay 官方規格。實作時重新查核實際用到的端點、地區與商家資格，記錄日期及差異；來源在第 20 節。不用部落格範例補出不存在的 API。

| 主題 | 已確認的設計依據 | 本版處理 |
|---|---|---|
| 同 Provider 的使用者識別 | 同一 Provider 下，使用者 ID 可跨 Channel 類型一致；不同 Provider 不同 [S23] | 同一攤點通服務的 Login／MINI App／Messaging 應正確配置，不能只比對暱稱／Email |
| LINE Login 加好友 | 須同 Provider、具管理權，Login Channel 只能連一個 OA；是使用者可選的動作 [S24] | 只連攤點通 OA，不要求每家店的 OA |
| MINI App 加好友 | 依所在地區、Channel 設定及 SDK 能力提供 linked OA 的加好友入口 [S25、S26] | 台灣採平台單一 OA；不套用僅其他地區可用的多 OA 功能 |
| 主動通知 | Messaging API Push 可送文字與 Flex；收件資格有條件，API 接受不代表一定送達 [S19] | 履約事件使用平台 OA 的 Push，不用過期 reply token |
| 訊息重試 | 支援的 Push API 可使用 retry key；同 key 同內容，首次請求起 24 小時內使用 [S20] | 本地去重加 Provider retry key，禁止逾期盲目換 key 重送 |
| MINI App 服務訊息 | 台灣顯示在「LINE MINI App 通知」，需相應認證與能力 [S04] | 不是本次目標聊天室，不能當作平台 OA 通知驗收的替代品 |
| 認證 | OA 認證、Certified Provider、Verified MINI App 是不同事項；台灣 MINI App 認證另有 Provider 條件 [S02、S30] | 分開列狀態與人工申請，不在程式中畫盾牌冒充認證 |
| Messaging API 設定 | OA Manager 啟用 Messaging API；Provider 選定後不能任意改動 [S27] | 先盤點既有 OA／Provider，不建錯後再嘗試搬移 |
| 交易訊息成本 | Push 計入帳號訊息用量；同請求多個 message object 不按物件數重算收件人 [S29] | 全平台共用額度，做每店歸因與額度告警，不宣稱交易通知免費 |
| Pay | API 商家憑證、Request／Confirm、查詢／退款各有契約 [S07–S14、S22] | 各店自己收款；不以回跳或 QR 核銷冒充付款成功 |

OA 認證不是後端訂單事件的替代品。認證狀態不明時，不在顧客介面聲稱「已認證」；仍可在實際帳號能力允許的隔離環境完成普通 Messaging API 測試，認證工作另外追蹤。

## 4. 平台 Provider／Channel、顧客與商家收款

### 4.1 Channel 對照矩陣

| 類別 | 歸屬與用途 | 秘密資料及權限 |
|---|---|---|
| 平台 LINE Login Channel | 攤點通既有 Web 登入，連到平台 OA | 平台 server-only 管理；記錄 Provider、Channel、callback 與環境 |
| 平台 MINI App Channel | 同一平台服務，多店路由；區分 Developing／Review／Published | 記錄各內部 Channel／LIFF ID／audience／Endpoint，不混環境 |
| 平台 Messaging API Channel | 攤點通唯一 OA 的通知與 Webhook | Token／Secret 只給受控平台後端；店家不能讀取或自訂 sender |
| 商家 LINE Pay Channel | 各收款商家的線上支付資格與帳號 | 每筆交易綁定真實商家、環境、版本與憑證引用 |

LINE Pay Channel 是付款系統的設定，不與 LINE Developers 的 Provider／Messaging Token 混為一談。

### 4.2 身分 namespace 與舊系統遷移

- 先確認攤點通是此平台服務的提供者，以及 Login／MINI App／Messaging 是否屬於正確的同一 Provider。不能為了省事把合作商家所有獨立 OA Channel 搬進平台 Provider。
- 使用經伺服器驗證的 `(environment, providerId, subject)` 對應既有平台顧客，記錄來源 Channel；Channel audience 仍必須驗證，不能因同 Provider 而放行任意 Token。
- 若現有 Login 與平台 OA 不同 Provider，禁止直接使用 Login 的 `sub` 推播或按電話／Email 合併。產出真實拓樸與安全遷移方案；只有具雙方帳號所有權證明的正式 account linking 可建立映射。無法證明就停用該顧客通知，不錯送訊息。
- 不把已發展的客戶身分一律刪除重建；舊訂單與 LINE 綁定保留可追溯性。帳號解除／重新綁定不能讓另一人接收先前訂單。
- 本版每筆新通知的 sender 固定為伺服器選定的 `PLATFORM_OA`。merchantId 只用於訂單授權與訊息中的店名，不能決定用任意商家 Token 發送。
- 既有 per-merchant OA 邏輯如已上線，不必刪掉其他產品用途，但本流程明確不使用。切換採每店旗標、時間邊界及通知 ledger，處理在途舊通知；不得把不確定已送的舊通知直接重送到新 OA。

### 4.3 平台會員不是商家員工

- 平台顧客 membership 與 Organization／Stall 員工 membership 是不同領域。LINE 登入不得自動加入任何店家員工角色，或啟用管理功能。
- 顧客只看自己的跨店訂單；這是「同一顧客的所有權查詢」，不是放寬商家 tenant isolation。
- 商家只能看本店履約所需顧客資料，不能以平台 memberId 查其他店消費、平台好友清單或整體 profile。
- 首次入會有清楚的服務條款／隱私告知；記錄接受版本、時間、來源。已入會者不重建。商家會員／集點／行銷名單不得隱含全選。

### 4.4 收款主體不變

預設為「顧客 → 該商家的 LINE Pay 帳號」。平台編排 API 與通知，不集中收餐費再轉付。單一平台 OA 可發多店通知，但每筆 PaymentAttempt 必須鎖定該筆真正 `merchantAccountId`、環境、API 版本與憑證版本引用。

商家未完成線上收款能力、合約或必要授權時，不啟用該商家的 LINE Pay；可沿用既有獲准支付。不能自動 fallback 到越好吃或平台 Pay Secret。費率、撥款與退款條件按實際合約核對，不寫死未查證價格。

## 5. 架構與概念契約

```text
攤點通平台 OA 圖文選單       合作店家 QR／Web／分享入口
          └──────────┬─────────────┘
                     ▼
            平台 MINI App／既有 Web UI
                     │
         LINE 驗證 → 平台顧客會員與既有 Session
                     │
       既有店家、菜單、購物車、訂單與履約核心
            │                         │
      每店 LINE Pay adapter       商家後台／POS／KDS
            │                         │
      Pay 狀態／對帳          製作完成／掃碼確認交付
            └──────────┬──────────────┘
                       ▼
           既有 Domain Events + Durable Outbox
              ├─ 原印單／庫存／SaaS Billing
              └─ 平台通知編排器（授權、去重、狀態檢查）
                        │
                唯一平台 OA Messaging API
                        │
           訂單卡片／餐點完成／已取餐通知
                        ▼
              該顧客的「攤點通」聊天室
```

### 5.1 必要工程邊界

- UI 是薄入口，重用訂單、支付、履約、會員核心；不新增 LINE 專用 Order 副本或不必要微服務。
- 若 Next.js API 與 Supabase Edge Function 都能觸發事件，使用共享 domain command／唯一事件 ledger，不能兩邊分別 Confirm、發訊或核銷。
- 資料庫短交易提交業務狀態與 Outbox；外部 Pay／LINE／印表機 I/O 不放在長時間 row lock 內。
- 通知 worker 有持久化佇列、租約、狀態版本與重啟恢復，不靠 serverless 記憶體或 `setTimeout`。
- 平台發訊服務不得接受商家自由輸入的 `to`／sender／完整訊息內容。由已授權訂單事件查出固定顧客、平台 OA 與允許模板，防止平台成為濫發代理。

### 5.2 概念 API 能力（先映射既有契約）

| 能力 | 必須驗證 | 結果與限制 |
|---|---|---|
| LINE session exchange | 原始 ID token、合法 Channel／環境、server challenge | 建立／旋轉既有 Session，不接受 body 指定角色 |
| Platform member join | 已驗證本人、條款版本、CSRF／冪等 | 建立／連結顧客會員，不賦予員工 membership |
| Platform friendship sync | 經驗證且對應同一顧客／Channel 的有效 Token 或已驗簽事件 | 更新好友觀察值與來源，不信任前端 `friendFlag` |
| My orders | 已登入顧客所有權＋分頁／店家篩選 | 只回自己的跨店訂單，不回完整商家客群 |
| Checkout／payment status | 原定價、訂單所有權、精確金額、冪等 | 沿用既有 Order／PaymentAttempt |
| Mark ready | 店員權限、店家、履約版本、未取消 | READY 與唯一 Outbox 同時提交，不代表已取餐 |
| Pickup preview | 已登入店員、正確店家、取餐 credential | 只預覽；不因掃碼或 GET 就核銷 |
| Confirm pickup | 店員交付確認、CSRF、版本、付款及履約規則、冪等 | 原子核銷＋PICKED_UP 事件，重複操作無新副作用 |
| Authorized resend | 本店權限、有效事件、通知狀態、冷卻及理由 | 受控補發或原操作重試，不能重改訂單 |
| Platform OA webhook | 固定 integration、raw body、正確簽章與 destination | 持久化與 eventId 去重後處理 |
| QR media fetch | 不透明圖片能力票據、期限／撤銷、節流 | 僅輸出 QR 圖，不暴露訂單詳情，不發生核銷 |
| Integration admin | 平台管理權／店家受限設定分開 | 只回遮罩狀態，所有敏感變更留稽核 |

契約必須有 schema、錯誤碼、授權、冪等及環境規則；名稱依 repo，不照此表再建立等價第二套 endpoints。

## 6. LINE 身分、平台顧客會員與 MINI App 初始化

### 6.1 身分驗證

1. 先重用 repo 的 LINE／OIDC／Supabase 整合能力，不發行不受既有 Auth 支援的自造 Supabase JWT，不另創永久 Token 登入系統。
2. LIFF SDK 僅在 Client 端初始化，採 singleton／狀態機避免重複 init、hydration 錯誤、OAuth 迴圈。使用與 lockfile 相容且經查證的 SDK 版本。
3. 前端傳送 `liff.getIDToken()` 取得的原始 Token 給後端；後端依 LINE 官方驗證流程檢查有效性、正確 Channel audience、issuer、期限及適用 claim，再取 `sub`。[S15、S18]
4. 不採信 `liff.getDecodedIDToken()` 或 `liff.getProfile()` 的前端 JSON 作為登入證明。前端傳來的使用者 ID、租戶或角色均不是可信任認證資料。
5. 當前部署只接受對應內部 Channel／環境的 Token。Production 不接受 Developing／Review audience，Preview 不接受 Production audience，不能以「同一 Provider」取消 audience 驗證。
6. 交換端點使用 same-origin／CSRF 防護、短效伺服器 challenge、嚴格 origin 檢查與節流，防止 login CSRF／Session fixation；Token 不進 URL、localStorage、分析事件或日誌。
7. 自行實作既有外部 LINE OAuth flow 時，使用可支援的 state、OIDC nonce、PKCE S256 等機制。LIFF 管理的登入則按 SDK 真正提供的介面處理；不可假裝能向 `liff.init()` 塞入任意 OAuth nonce，或要求 Token 必須有無法實際取得的 claim。
8. 首選最少 scope。身分用 `openid`；本版若使用 `liff.getFriendship()`，按官方要求配置 `profile`，並說明用途。不為點餐預設索取 Email；暱稱與頭像不當真實姓名證明。[S26]
9. LINE 授權、平台顧客入會、加入平台 OA 好友、各店會員與行銷同意分開。一次順暢 onboarding 可完成多個步驟，但資料與同意不能合成一個不可拒絕選項。
10. 帳號合併只能沿用已驗證的 account linking 流程，不按 Email 相同自動合併 Google／Apple／LINE 身分。

### 6.2 Session、購物車與返回

- 採既有安全 Session 策略；若用 cookie，驗證 HttpOnly／Secure／SameSite 與 LINE Pay 回跳相容性，不直接把所有 cookie 改為 `SameSite=None`。
- 若既有 Supabase browser flow 必須使用前端 Session，維持其官方受支援流程並評估 Token 暴露風險；不為符合 cookie 偏好重建整套 Auth。LINE 原始 Token 不另作持久儲存。
- 購物車需綁定既有訪客 Session 或顧客；登入後合併只允許同一合法擁有者與指定店家，切換 LINE 帳號不得沿用前一人的訂單存取權。
- 清空 cookie、重開 MINI App 或付款後無 Session 時，先重新驗證身分，再讀取訂單；僅憑 `orderId`／`transactionId` 不可看到姓名電話、餐點或其他私密資料。
- 顧客付款進行中，伺服器仍可依受控 PaymentAttempt 恢復交易；交易確認不能完全依賴瀏覽器持續存活。
- 身分 Token 過期、拒絕授權、SDK 載入失敗時有明確重試及返回方案。保留可公開瀏覽菜單的能力，不用無限登入重新導向。

### 6.3 永久連結與深層路由

- 使用控制台實際產生的 MINI App LIFF ID，永久連結以官方規則計算相對 Endpoint 路徑，不任意拼出不存在的 Channel。[S06]
- 店家頁、購物車與訂單頁均在允許的 Endpoint 範圍內。正確處理 LIFF 初始化與原有 router，不在初始化前破壞 SDK 所需參數。
- 建立最小的 `LineEntryContext`，保存來源、店家及安全 return target；不能把該物件當付款、會員或租戶授權。
- 私人訂單分享預設禁止。分享店面／餐點時，移除 Token、Session、顧客識別碼、付款資訊與訪客存取憑證。
- `returnTo` 僅可為受控相對路徑；拒絕外部 origin、雙重編碼、`//host`、非 HTTPS 協定與繞過路徑。

### 6.4 平台入會與好友流程

1. 初次 LINE 登入後，顯示「使用 LINE 加入攤點通」及真實平台條款／隱私連結，使用者確認後才記錄正式顧客入會；不得把 Token 驗證成功自行視為接受所有商家條款。
2. 重用既有 Customer／User profile，`provider+subject` 唯一映射防止重試建立多名會員。曾用 Google／Apple 的顧客只能透過可證明兩方擁有權的綁定連結，不以 Email 相同自動合併。
3. 入會後顯示「加入攤點通 LINE 官方帳號，接收本次訂單與取餐通知」。使用 Login add-friend option 或 MINI App 實際支援的 linked OA 能力；取消加入仍可沿用可用的訂單查詢，不強制行銷同意。[S24、S25]
4. LINE Login 的 `friendship_status_changed=false` 只代表狀態未改變，不能推斷一定未加好友。使用與該本人／Channel 相符的 friendship API／事件檢查。[S24]
5. `liff.getFriendship()` 的前端結果用於 UI 提示；後端需以已驗證 Token 的官方查詢或已驗簽的 follow／unfollow 事件作可追溯判斷。不能讓客戶端直接把資料庫 `friend=true`。
6. `liff.requestFriendship()`／加好友連結只是發起使用者動作，返回不代表成功；檢查 SDK、LINE 版本、地區和官方返回語意，完成後重新同步好友狀態。能力缺少時給安全的官方加好友入口，不使用私有技巧。
7. 好友狀態至少有 `UNKNOWN`、`FRIEND`、`NOT_FRIEND_OR_BLOCKED`，附觀察來源與時間；官方回傳無法區分未加入／封鎖時不假裝能精準區分。事件晚到時按 timestamp／版本防止舊 follow 蓋掉新 unfollow。
8. 推播資格：LINE API 對「近期曾一對一傳訊」的非好友另有條件例外；本版產品預設採已確認好友再主動發交易通知，不依賴短期例外作長期營運保證。這是保守產品策略，不宣稱 LINE 一律禁止所有非好友 Push。[S19]
9. 好友關係可能在檢查後變動，因此即使判斷 eligible，也不承諾 API 200 代表送達。訊息未啟用時，結帳／訂單頁寫「尚未啟用 LINE 取餐通知，請於訂單頁查看」，不寫「一定會收到」。
10. 加好友早於入會：先保存最小、受保護的 OA 關係事件；之後本人成功登入及入會才建立顧客關聯。不能將所有 OA 好友批次自動註冊成會員或讀取所有好友清單當必要依賴。
11. 入會早於加好友：允許之後補連結；只補發仍有效且具所有權的進行中訂單摘要或最新必要狀態，不重播全部歷史訂單通知。
12. 客戶解除綁定／封鎖時，停用後續不符合條件的通知；保留按政策必要的訂單與稽核。刪除會員流程沿用現行資料保存規則，不能刪掉法定／爭議所需付款事實。

### 6.5 訂單所有權與切換帳號

- 在下單時固定 `platformCustomerId`、合法 LINE identity 及通知 recipient 關聯；後續 worker 不能從「最近一次登入者」推導收件人。
- LINE 綁定變更、customer merge 或 OA 遷移必須經受控流程；不悄悄把 in-flight 訂單改送另一個帳號。需要重新指定時驗證所有權、撤銷舊待發任務並留稽核。
- 訪客訂單入會後歸戶，要同時證明原安全訪客 Session／一次性 claim 和新登入身分；僅知道短取餐號、姓名、電話、QR 圖或 orderId 不足以取得訂單詳情。
- 同一顧客可在多家店有訂單，但跨店「我的訂單」API 必須以顧客本人 filter；商家與平台支援的權限不共用這個顧客入口。

## 7. 平台入口、訂單卡片、通知文案與圖文選單

### 7.1 MINI App 與既有 Web

沿用攤點通品牌、設計 tokens、組件及多語系；預設繁體中文、TWD，顯示時區 `Asia/Taipei`，資料時間沿用一致 UTC 策略。

必備頁面／狀態：合作店家入口、原店家菜單與加料、單店購物車、取餐時段、既有結帳、付款返回、平台會員中心、本人跨店訂單列表、單筆訂單動態狀態與取餐碼、門市聯絡頁。

- 店家 QR 深連結仍直達指定店家，不逼顧客每次回平台重新搜尋。
- 店家切換不得混合購物車；同一平台會員也不能一次用 A 店收款帳號收 B 店的餐費。
- 訂單頁清楚分開待付款、付款確認中、已付款待接單、製作中、可取餐、已取餐、取消、退款中與已退款。
- 「我的訂單」按進行中／歷史及店家篩選；僅顧客本人跨店可見，不把它改成所有租戶可查的 API。
- 會員中心提供 LINE 綁定、平台 OA 通知可用狀態、條款及必要設定，不新增集點／優惠／付費會員。
- Web 與 QR 原路徑仍可用。主 LINE 流程不主動導外部一般瀏覽器，但允許官方授權及 Pay 所需切換；不宣稱完全零切換。

### 7.2 訂單成立卡片：必須真實可用

使用平台 OA 的 Flex Message，搭配必要的 `altText` 與可操作按鈕；用官方 validator 和實機驗證，不交一張截圖假裝功能完成。[S19、S28]

| 區塊 | 必須顯示／處理 |
|---|---|
| 品牌與門市 | 攤點通品牌、實際店名及分店；不改 sender 偽裝成不同商家 |
| 訂單識別 | 對外訂單號／取餐號、下單時間與本次狀態快照 |
| 金額與付款 | 精確訂單金額、幣別、真實付款狀態；現金未付不得寫已付款 |
| 取餐資訊 | 預約／預估時間與實際可取餐狀態分開；門市／取餐位置清楚 |
| QR 區 | 自建、可掃、具期限及服務端一次性核銷的取餐 QR；詳見第 11 節 |
| 說明文字 | 尚在製作：「請於餐點完成後，出示此碼取餐」；READY：「餐點已完成，請出示此碼取餐」 |
| 訂單詳情 | 合法 MINI App 深層連結，登入後驗證本人所有權；不能是永久免驗證的個資連結 |
| 聯絡店家 | 對應本筆訂單的分店聯絡頁／經驗證電話，不誤連平台客服或另一店 |

訂單卡片是發送當時快照，不能假設 LINE 已發出的 bubble 可被任意動態修改。後續狀態以新訊息及訂單詳情頁為準；卡片的 QR 是否仍有效，以服務端核銷狀態為準。

訂單成立通知不是每個付款事件都送一次。線上支付正常流程在訂單可確認成立、付款結果已知時送一張；現金單按原允許成立條件送。若未成立但需顯示待確認，內容必須明示，不假裝店家已承接。

### 7.3 餐點完成、已取餐與異常文案

以下是本版模板要求，使用程式安全插值，店名與文字長度需驗證；示例值不是正式資料。沒有合法稱呼就用「您好」，不用截圖裡的顧客姓名。

**餐點完成：**

```text
您好，您在「{storeDisplayName}」的訂單餐點已完成，請取餐。
取餐號碼：{pickupNumber}
取餐門市：{branchDisplayName}
請出示訂單中的取餐 QR Code，由店員確認交付。
```

搭配「查看訂單／出示取餐碼」「聯絡店家」操作，必要時同一次 Push 中加小型 Flex 卡片。這是交易通知，不加折扣、廣告或跨店推薦。

**已完成取餐：**

```text
您好，您在「{storeDisplayName}」的訂單已完成取餐。
取餐號碼：{pickupNumber}
完成時間：{pickedUpAtLocal}
感謝您的訂購。
```

只有店員實際交付核銷成功才觸發此訊息；支付 Confirm、列印成功、預估時間已到、顧客開啟 QR 都不算交付。

**取消／退款：** 沿用既有交易模板，但準確區分「訂單取消」「退款處理中」「退款已完成」。不能以商家按取消就寫款項已退回。

### 7.4 圖文選單與歡迎訊息

預設使用平台四入口，可依既有版面調整但不能出現無效連結：

| 入口 | 目的地 |
|---|---|
| 立即點餐／合作店家 | 平台可公開合作店家入口；指定商家 QR 另維持直達 |
| 我的訂單 | 本人跨店進行中及歷史訂單 |
| 會員中心 | 平台顧客資料、LINE 綁定及交易通知狀態 |
| 聯絡客服 | 平台客服／常見問題；單筆訂單仍有獨立「聯絡店家」 |

歡迎訊息示例：「歡迎使用攤點通。您可以選擇合作店家點餐，並在這裡接收訂單與取餐通知。點選『立即點餐』開始；既有訂單請至『我的訂單』查看。」對未知／未完成通知設定的顧客，不加「已完成會員註冊」等錯誤承諾。

- 使用真實 QIDAIGO 品牌素材，不仿製 dudoo 吉祥物或官方盾牌。沒有素材時交付清楚標示的版面資產及缺項，不能冒充已發布。
- 產出圖片版面、操作區 JSON、deep-link 對照與 dry-run／apply／restore 方式。先核對當日 LINE 支援尺寸、格式及限制。[S05、S17]
- 先確認 OA Manager／Messaging API 管理來源。API 查不到 Manager 的選單不能推定不存在；不覆蓋既有歡迎訊息／第三方 Bot。
- 腳本限定平台管理員，先建立資產與差異，再經授權切換。保存可取得的原配置及人工回復說明；不謊稱 API 可完整備份不開放的 Manager 內容。
- LINE 桌面沒有相同手機圖文選單體驗時，提供可用的訊息連結入口；桌面不強行模擬手機全部功能。

### 7.5 版面、圖片與可用性

- 驗證窄螢幕、深淺色、長店名、Emoji、200% 字體、safe-area、鍵盤、返回鍵、讀屏與清楚的錯誤文字；觸控目標以至少 44 CSS px 為工程目標。
- Flex JSON／altText／按鈕文字／圖片 URL 依官方規格檢查，避免把 API 接受當成 iOS／Android 都無截斷。
- QR 高對比、安靜區、足夠尺寸；不在 QR 上疊 logo 或過度壓縮到不能掃描。圖片抓取方式遵守第 11 節，不用第三方 QR 服務傳送憑證。
- 本人訂單頁不可公共快取；公開菜單按店家／語系／版本隔離。QR 圖片有單獨的受限媒體政策，不能誤把整張個資訂單卡當公共靜態頁。
- 禁止在付款／登入／取餐憑證 URL 記錄完整 analytics 或 HAR；測試影片與截圖使用合成資料。

## 8. 訂單、付款與退款狀態設計

### 8.1 僅映射、不強制改名

以下為概念狀態，不是 LINE Pay 原始回傳值，也不是強制替換 repo enum：

```text
PaymentAttempt:
CREATED → REQUESTING → PENDING_AUTH → CONFIRMING → SUCCEEDED
                    ↘ UNKNOWN / RECONCILING
PENDING_AUTH → CANCELLED / EXPIRED / FAILED（須有可驗證依據）
UNKNOWN / RECONCILING → SUCCEEDED / FAILED / MANUAL_REVIEW

RefundAttempt:
CREATED → PROCESSING → SUCCEEDED
                    ↘ UNKNOWN / FAILED / MANUAL_REVIEW
```

Order／Payment／Refund 各自管理狀態。付款成功不代表餐點已完成；退款成功不自動表示所有品項可重新入庫；訂單取消不代表金流已退款。

### 8.2 Checkout 與保留資源

1. 後端由既有 cart／商品資料重新計價，驗證店家接單、商品啟用、庫存、規格、優惠、取餐容量、訂單上下限及用餐方式。
2. 金額使用 repo 的精確 Money／Decimal 契約，LINE Pay TWD adapter 明確轉為其規格接受的單位與整數規則。不能混用「元」與「分」，不能用浮點累加再隨意 round。
3. 保存價格、稅費、優惠、店家、用餐／取餐資料的訂單快照與顧客確認版本。
4. 先持久化既有 Order／PaymentAttempt，再呼叫 Provider；不可付款成功後才第一次建立本地訂單。
5. 沿用庫存與時段保留邏輯，補上到期、並行 checkout、最後一份商品與付款進行中的競態處理。不為同筆訂單重複扣庫存。
6. 本地保留期限與 Provider 付款可用期限需協調。Provider 仍可能付款／Confirm 結果未定時，不能單純本地逾時就把同一資源無條件售予下一人。
7. 付款後才發現本地訂單逾時、商家無法接單或資源已失效時，進入顯式異常流程；不可丟棄已付款事實，也不可不經可履行性檢查自動復活訂單。
8. 依已核准商家規則處理退款補償；沒有規則時建立待處理任務與告警，不靜默吞掉交易。

### 8.3 冪等與多次付款嘗試

- Checkout key 至少綁定環境、商家、訂單／購物車版本與操作；同 key 不同 payload 拒絕，不覆蓋原交易。
- 每個訂單可以有多個歷史 PaymentAttempt，但同一時點只有一個允許進行的付款流程。用資料庫唯一條件／鎖定與版本控制，不依賴單一 Node process 的記憶體鎖。
- 使用穩定、唯一的商家端 Provider order ID，明確區分本地訂單與付款嘗試。重送同一請求不能每次隨機產生新的 Provider order ID。
- 每筆付款嘗試綁定商家憑證與 API 版本快照；管理員更新預設收款帳號後，舊交易仍用原帳號查詢／退款。密鑰輪替由安全的版本引用管理，不把 Secret 複製到交易列。
- 同一筆 Confirm、退款、訂單事件、備餐通知、列印與 SaaS 計費都需要各自的唯一操作鍵。
- 無法證明前一嘗試未扣款時，不提供立即再次 LINE Pay／其他金流／現金重付的捷徑。先查詢或轉人工確認。
- 若外部真的產生兩筆已扣款交易，完整記錄兩筆，將第二筆標成超收異常並交由受控補償。不得以唯一索引衝突為由隱藏真實外部金流。
- 只能保證本地冪等與受控重試；不能宣稱跨外部付款服務具有未經證實的 exactly-once 傳遞保證。

### 8.4 未知結果與恢復

請明確測試「LINE Pay 已處理，但我方沒收到 response」和「我方收到 response，但 DB commit 前服務崩潰」。

- Request timeout：先依已持久化 operation、可能取得的 transaction ID 與官方支援查詢恢復；查不到已確認交易，不代表先前 Request 從未建立。缺少足夠資料時保持 UNKNOWN／人工處理，不盲目建立新付款。
- Confirm timeout：對帳／查詢先行，再依可驗證結果更新本地；不能單純改 FAILED 或重複扣款。
- Refund timeout：鎖住退款 operation 與可退款餘額，先查實際退款紀錄；沒有可驗證 Provider 冪等保證時不得盲目再次部分退款。
- durable worker 需要重試退避、抖動、截止時間、租約、防重入、可觀測狀態與人工升級。重啟後仍能接續。
- 只對明確安全／官方允許重試的情況重試；`429`／暫時錯誤／斷線不代表每個 mutation 都能自動重送。
- 對帳頁顯示資料庫狀態、Provider 查核結果、最近檢查時間及待辦，不把支付平台結算入銀行的日期等同於 API 付款成功時間。查明細採官方支援的查詢條件與已完成交易／退款資料；查不到明細不等於未完成的 Request 不存在。[S22]

## 9. LINE Pay adapter：必須完成真實協定

### 9.1 版本與 Endpoint

新整合以經官方及商家能力確認的 Online API v4 為預設評估方向。若既有 v3 已運作，沿用並補強，必要的版本遷移另以 ADR、相容測試及旗標控制，不強制同時實作兩個完整新版本。

v4 官方路徑供核對：[S07、S10–S14、S22]

```text
POST /v4/payments/request
GET  /v4/payments/requests/{transactionId}/check
POST /v4/payments/{transactionId}/confirm
GET  /v4/payments
POST /v4/payments/{transactionId}/refund

Sandbox host:    sandbox-api-pay.line.me
Production host: api-pay.line.me
```

- 對外 API host 從已驗證環境映射，不接受前端或租戶任意指定 base URL，避免 SSRF／憑證外送。
- Query 名稱、集合參數格式、required 欄位、timeout 與回傳 schema 依當日端點文件／官方測試確認，不照抄示例中的拼字、HTTP 或 URL 拼接錯誤。
- 本次採單次付款的基本流程。若既有系統使用 capture-separated，保留且明確區分 AUTHORIZED 與 CAPTURED；不能將授權但未請款顯示為已結清。不新增預先授權扣款或訂閱扣款。[S09]

### 9.2 伺服器簽章與精度

- LINE Pay Channel Secret 只存在伺服器 Secret store。依官方規格產生 HMAC-SHA256、Base64 及每次請求 nonce，設定對應的 `X-LINE-*` headers。[S08]
- `POST` 的簽章 message 包含 Channel Secret、API path、實際送出的 JSON body 與 nonce；JSON 只序列化一次，簽的字串就是送出的 bytes。
- `GET` 的 query string 生成、編碼、排序與簽章使用同一份結果；依官方定義處理分隔符，不能手動組錯 `?`／`&`。
- 使用獨立的測試向量確認簽章，不能讓測試與實作共用同一個錯誤字串組合方式。
- `transactionId`／`refundTransactionId` 必須從 HTTP 原始 response 開始無損解析並以字串或可安全序列化的 64-bit 型別保存。[S07]
- 不可先 `response.json()` 或 `JSON.parse()` 轉成 JavaScript Number 再 `String()`；精度已遺失無法補回。採可靠的 lossless parser／型別化 adapter，避免對所有 JSON 數值盲目 regex 替換。
- 測試 fixture 至少包含大於 `Number.MAX_SAFE_INTEGER` 的未加引號整數，以及 API 路徑、DB、JSON 回傳的完整 round-trip；可用合成值 `2026092201234567891`。
- 不將 HTTP 200 當成付款成功；依各 endpoint 的 `returnCode` 與資訊判斷。[S07]

### 9.3 狀態查詢不能誤判

`Check payment request status` 的以下語意要逐項測試，不可共用「0000 一律已付款」的 helper：[S11]

| returnCode | 此 check endpoint 的意義 | 本地動作 |
|---|---|---|
| `0000` | 顧客尚未完成 LINE Pay 授權 | 繼續待付款，不能出單 |
| `0110` | 已完成授權，可進行付款確認 | 由後端對既有授權 checkout 執行受控 Confirm |
| `0121` | 取消或授權等待逾時 | 依現有交易狀態與資源規則終結，避免覆蓋已付款 |
| `0122` | 付款失敗 | 記錄可驗證失敗，依規則允許新的操作 |
| `0123` | 付款已完成 | 必要時查明細比對訂單、商家、金額及結清狀態，再修復本地 |

其他 endpoint 的 `0000` 只代表該次 API 操作成功，須按 Request／Confirm／Refund 各自語意判定。Request 成功不是已付款；Check 授權成功不是已請款。

### 9.4 回跳與後端確認

- 伺服器產生固定 HTTPS confirm／cancel URL，且兩者都來自受控設定，不採信瀏覽器傳入的 URL。[S13]
- 使用高熵、短效、具用途綁定的自有 return state，關聯 PaymentAttempt、環境與商家；儲存安全的雜湊／引用，防止偽造和跨訂單替換。
- LINE Pay 會回傳的 `orderId`／`transactionId` 必須與本地綁定資料比對；不要自行把尚未取得的 transaction ID 塞入原始 callback URL。[S13]
- 重放 return state 只能取回同一操作結果，不能再發起一筆扣款；此 state 不是讀取訂單個資的通行證。
- 基本 browser return 不假定附有 Messaging API 的 `x-line-signature`。不得套用錯誤的 OA Webhook 驗證協定導致付款不能完成。
- 付款完成只來自受控、已認證的 LINE Pay server API 回應／查詢證據；callback query、前端 `paid=true` 或商家手動改欄位都不能冒充證據。
- 回跳可以觸發交易恢復，但只操作該 PaymentAttempt。驗證完成後轉回乾淨的 MINI App 訂單狀態頁；Session 不在時重新認證後才顯示私密內容。
- cancel return 是顧客流程訊號，不足以單獨撤銷已成功扣款的本地紀錄。和並行 Confirm／對帳一起處理。
- 不假設 LINE Pay 自動提供類似其他支付業者的通用 `payment.succeeded` Webhook。只有官方文件與商家設定真正提供某種 server callback，才實作其對應能力與驗證；否則使用官方基本流程及受控查詢。

### 9.5 Refund、對帳與報表

- 支援商家有權限操作的全額退款；部分退款依實際商家能力與既有訂單模型啟用，能力不足須明示停用。[S14]
- 退款金額由後端計算，明確傳送需要退的金額；不可因遺漏 optional `refundAmount` 而意外全退。
- 同時扣除已成功退款與進行中／未知結果退款的保留額，防止並行超退。
- 退款操作要原因、操作者、角色、原始交易、冪等鍵、Provider response 與時間；前端不能改 `refundStatus` 直接成功。
- LINE Pay 自有交易對帳與既有 SaaS 收費對帳分開：餐費付款、退款、店家接受、訂單完成不是同一事件。
- 只在既有完成／淨完成訂單事件成立時，依原本 Billing 規則計算服務費；部分退款、整單退款、取消是否沖銷沿用現有政策，不擅改。
- `payment confirmed` 的本地交易同時提交狀態與 Outbox。外部 KDS／列印失敗不回滾已扣款事實；重送走同一個事件鍵。
- 對外裝置不一定有 exactly-once 能力。若列印回應遺失，顯示「列印結果不明」並提供授權重印，不能用無限重試造成重複出餐／開錢櫃。

## 10. 平台官方帳號的交易通知編排

### 10.1 固定 sender，不能退回舊架構

這次的通知模式固定為 `PLATFORM_OA`。訂單卡片、`ORDER_READY`、`ORDER_PICKED_UP` 及必要取消／退款通知，全部由攤點通平台 OA 的 Messaging API 發給該顧客一對一聊天室。

- 不要求合作店家提供自己的 Messaging API Token。
- 不把「LINE MINI App 通知」服務訊息當備援、雙送或驗收替代。既有其他用途可保留，但本流程不呼叫其 adapter。
- 不從 LINE Pay 的交易資料推測顧客 LINE ID；只用經驗證、與平台會員及該訂單固定綁定的 identity。
- 不用 `liff.sendMessages()` 模擬平台主動通知，不保存首次登入的 reply token 等幾十分鐘後用，也不推到 group／room 曝露訂單。
- 使用 `POST https://api.line.me/v2/bot/message/push`，Token 來自平台 server-only 設定；實際 endpoint/schema 依官方再核對。[S19]
- 每筆訊息清楚標示是哪一家店與哪一筆訂單；不依 `merchantId` 覆寫 sender 名稱／頭像成別人的品牌。

### 10.2 三個主要語意事件與發送條件

下列是應用層概念事件，不是 LINE 官方 Webhook；映射現有 domain event／履約版本，不必強制修改 enum。

| 事件 | 來源 | 發送條件 | 內容 |
|---|---|---|---|
| `ORDER_RECEIPT_AVAILABLE` | 既有訂單成立流程，結合正確付款語意 | 訂單對本人有效；付款／現金狀態可如實表達；同訂單首次收據事件去重 | 訂單 Flex 卡片、金額、店家、取餐 QR、詳情／聯絡 |
| `ORDER_READY` | 店員／KDS 通過授權的整單製作完成 | 後端已提交 READY，未取消／核銷；非單品部分完成；收件資格有效 | 餐點完成、可取餐通知 |
| `ORDER_PICKED_UP` | 店員實際交付後的原子核銷 | 唯一核銷成功，符合原付款與交付規則 | 已取餐、時間、店家與取餐號 |
| `ORDER_CANCELLED`／退款結果 | 既有可驗證的取消／退款流程 | 實際狀態與模板一致 | 必要交易異常通知 |

同一筆正常訂單通常是三次不同時間的通知；不是把三個階段在結帳當下全發出。若 READY 尚未發而顧客已完成取餐，抑制過時 READY，不能為湊三則而再叫顧客取餐。

付款事件與 ORDER_RECEIPT_AVAILABLE 需在既有 idempotency／receipt ledger 收斂；`CREATED`、`CONFIRMED`、`payment succeeded` 不能各自多發一張相同成立卡片。另發付款變更通知只在確有必要、不同語意且去重時允許。

### 10.3 Durable Outbox 與收件人鎖定

1. 業務狀態與 Outbox 在同一資料庫交易提交；worker 只讀已提交事件。DB commit 失敗不能已經對顧客發「餐點完成」。
2. 唯一鍵至少綁定 environment、platformOaIntegration、orderId、semanticEvent、businessEventVersion、recipient identity。不要用秒級時間戳當去重。
3. 發送前驗證事件／訂單所有權、店家啟用狀態、會員通知關聯、最新好友觀察及用途；merchant payload 不能任意改 `to`、店名、連結或顧客。
4. 首次送出前持久化不可變的 recipient、sender integration、templateVersion、payload hash、受保護必要內容、retryKey、首次請求時間。相同 Provider 重試不得換內容或收件人。
5. 工作租約／版本保護並行 worker。程序崩潰後可恢復；發送成功但 DB 未記錄的情況，使用原 retry key 恢復，而非建立另一則訊息。
6. 處理更晚抵達的舊事件：送出前若已取消／退款導致不可履約、已取餐或 credential 已撤銷，抑制未送出的過期取餐通知；依最新狀態產生必要的另一種訊息。
7. 若外部請求已在途，無法保證取消訂單能召回已發訊息。記錄事件時間與發送時間，提供最新訂單頁，不能聲稱全系統零亂序／可撤回所有舊卡片。
8. 顧客重新登入、手機關閉、小程序離開前景，不影響後端發送。不可等顧客再打開頁面才發 READY。
9. 正常環境以 READY 提交後 10 秒內發出首次 Push 為工程目標，不是顧客送達 SLA；測量 queue lag。若現有排程無法達成，提出沿用基礎設施的持久化即時觸發＋恢復方案，不用不可恢復的 fire-and-forget 假裝即時。

### 10.4 LINE Push 冪等、錯誤與可觀測狀態

- 第一次請求就附合法 UUID `X-Line-Retry-Key`；重試沿用相同 key／recipient／body。有效期限是首次請求後 24 小時，不能每次重試延長。[S20]
- HTTP 2xx 記錄 `PROVIDER_ACCEPTED`；已被接受的 retry key 回 409 時，核對官方語意與 `x-line-accepted-request-id` 後視為同一次已接受，停止重送。一般無關 409 不可無條件當成功。
- timeout／5xx 依官方允許方式退避加抖動；保留操作狀態與 request ID。400 格式錯誤、401／403 憑證與權限錯誤不盲重試。429 必須區分速率／配額原因，依實際規格處理；額度用盡等待管理員處理，不無限循環。
- key 超出有效窗、未知結果未解決時，轉人工，不自動換新 key 當作從未發送。
- 狀態至少表示：`QUEUED`、`IN_FLIGHT`、`RETRY_SCHEDULED`、`PROVIDER_ACCEPTED`、`SUPPRESSED`、`FAILED`、`UNKNOWN`／`MANUAL_REVIEW`。可映射現有 enum，但 UI 的語意不能錯。
- UI 顯示「待發送」「LINE 已接受」「暫時失敗待重試」「未啟用通知」「已停止過時通知」「需人工確認」。不要顯示無證據的「顧客已讀」或「確定送達」。[S19、S20]
- 若 Push 使用 `notificationDisabled=false`，只能表示未主動靜音此次通知；顧客裝置通知權限、勿擾或聊天室靜音仍由顧客控制，不承諾必響鈴。[S19]
- 通知失敗不回滾已付款／READY／已取餐事實。通知只是副作用，訂單頁及店家現場操作仍是查詢和履約依據。

### 10.5 平台共用額度、節流與補發

- 用既有排程／監控讀取 `/v2/bot/message/quota`、`/v2/bot/message/quota/consumption` 等官方能力；依實際 Taiwan OA 方案顯示額度，不能套用日本價格。[S29]
- Push 用量由全平台 OA 共同負擔。按 store／event 記錄內部歸因，採公平排程、每店限流、全局節流與READY優先權，避免單店耗盡其他店取餐通知資源。
- 一次對一人的 Push 可含符合限制的文字＋Flex，不因同一請求有兩個物件就自行算兩次收件。預算估算明示「正常流程三次事件約三次對單人的發送」，不是固定每單一定計費三則或保證實際帳單一致。
- 不主動升級 OA 付費方案、不用免費 reply trick 代替延遲 Push。用量超限與認證資格是不同阻礙。
- 「補發通知」只對該店該筆有效事件，限具權限人員，記錄理由、冷卻及次數；區分 Provider 原請求重試與經授權新補發，不能重改 READY、重核銷或重計費。
- 已取消／已取餐不可補發「請取餐」。通知結果未知時先處理原操作，不把手動按鈕當成繞過去重的入口。

### 10.6 平台 Webhook

- Webhook URL 固定對應平台 integration；用 Messaging Secret 對未修改的 raw body 驗證 `x-line-signature`，安全比對，之後才 parse；不能用 Pay Secret。[S16]
- 驗簽後比對 destination，按 webhookEventId 去重，空 events 合法檢查正確回應。原 body、Channel Token、reply token 不進一般日誌。
- 成功持久化後才 ACK，durable worker 處理 follow／unfollow／必要的一對一指令；允許合法延遲重送並按事件時間避免狀態倒退。
- 若顧客傳「我的訂單」，可在有效 reply window 內回本人驗證入口；不能向群組或未驗證收件對象貼私人訂單。Reply API 不用作延遲餐點完成通知。
- 既有平台 OA 若已有第三方 Bot／Webhook，先讀取設定與路由能力；無法安全共存時列阻礙，不默默更換 URL 導致其他功能失效。

## 11. 製作完成、取餐 QR 與店員交付核銷

### 11.1 履約狀態與既有 enum 映射

概念履約流程為：

```text
接單 → 製作中 → 餐點完成／可取餐（READY）
                         → 店員確認實際交付（PICKED_UP／履約完成）
```

付款是獨立維度。若既有 `COMPLETED`、`QR_PAYMENT_COMPLETED_PENDING_FULFILLMENT` 或其他名稱表示支付結束，不能直接用它觸發「已取餐」。先畫出實際狀態圖，找到能代表實際交付的 domain command／事件；缺少時最小擴充既有履約紀錄，不為方便改壞原財務流程。

READY 不觸發原已完成單 Billing；核銷也不能和既有 completion handler 各計一次費。按照 repo 已確認的完成／淨完成政策，透過同一 ledger 執行。

### 11.2 店員「製作完成／通知取餐」

- 在原商家後台／POS／KDS 的進行中訂單提供明確按鈕；當前使用者須有該店 `update fulfillment` 等實際權限。
- 只有所有需要製作的有效品項完成、或符合既有整單完成規則才轉 READY。部分品項、取消品項、改單、打包狀態依真實核心處理，不能第一道菜完成就叫整單取餐。
- 關閉 KDS 的小店也能從既有訂單列表完成同一動作；不強迫每家店開 KDS 才能推播。
- 後端確認未取消、未核銷、店家歸屬及版本後，以原子狀態轉移＋Outbox 發出一次 `ORDER_READY`。
- 連點、雙店員同時點、離線重連補送或多 API 入口皆同一個業務結果；不得發多則、重印多張或重開錢櫃。
- 不能根據預估取餐時間、付款成功或列印完成自動視為 READY。
- 店員操作成功即顯示「餐點已標示可取餐」，另列「通知待發送／LINE 已接受／需處理」；通知異常不能把餐點狀態退回製作中。
- 已 READY 要更正回製作中，僅沿用有權限及原因的既有更正流程；不能為反覆切狀態無限制重送。記錄履約版本，必要顧客更正通知另建受控事件。

### 11.3 QR 的用途與預設安全設計

取餐 QR 是本筆訂單的**受限交付憑證**，不是登入 Token、付款成功證據或訂單詳情的公開通行證。

1. 優先沿用既有安全取餐 credential；不足時以密碼學安全亂數產生至少 128-bit 熵的不透明 token，含用途版本，不使用可猜的 orderId／電話／短流水號。
2. 伺服器保存雜湊供核對、綁定 order／store／environment／版本、有效期限、撤銷／核銷狀態。若需重繪 QR，另以 server-only 加密 payload 保存可還原材料，金鑰與 DB 分離；不能一邊只存不可還原 hash、一邊宣稱能無條件重繪原 token。
3. QR payload 預設為本系統掃碼器可辨識的非 HTTP 字串，例如 `qidaigo:pickup:v1:<opaque-token>`；不放姓名、電話、金額、LINE subject 或秘密 API 金鑰。
4. 掃碼器解析後呼叫已登入店員的預覽／核銷 API。若沿用安全 HTTPS 取餐連結，任何 GET／連結預覽只做安全顯示，不自動核銷或改訂單。
5. 沿用實際 pickup deadline；沒有既有政策時採可配置的 `PICKUP_TOKEN_GRACE_MINUTES=120`，以有效的 scheduledPickupAt／estimatedPickupAt，否則 createdAt 為基準。此為可調工程預設，不是 LINE 規定；上線前由商家確認，測試預訂隔日、延遲備餐及時區。
6. 預定時間／履約更改需同步處理 credential deadline／版本。過期但合法延遲取餐，由具權限店員檢查並受控延展或重發，不能每次掃描就自動延長所有 token。
7. 顧客看得到初始 QR 不代表當下可以核銷；後端仍須檢查 READY、付款規則、未取消、未使用與店員權限。
8. 重發新 credential 必須撤銷舊版，並使訂單頁顯示新版；不可讓每次重試產生很多同時有效取餐憑證。
9. QR 截圖可以被轉傳，不能保證僅本人持有或防截圖；以限定用途、店員核對、期限與一次性核銷控制風險。無需將全部個資印上 QR 或依臉部辨識交付。

### 11.4 LINE 卡片 QR 圖片的提供方式

LINE 抓取 Flex 圖片不會帶本系統使用者的 Session。必須實作能讓 LINE 實際取得、但不會公開枚舉顧客資料的圖片端點。[S19、S28]

- QR PNG 由自有服務／既有安全儲存產生；不用外部 QR 網站 API 傳送 token，也不用 data URI、localhost 或前端 Blob URL 代替正式 HTTPS 圖片 URL。
- 圖片 URL 使用與取餐 token 分離的高熵 `mediaAccessToken`，只具有取得該張 QR 圖的能力；server 存 hash、期限及最小關聯，不把會員 JWT 或付款 credential 放在 URL。
- 媒體存取票據是可轉傳的能力票據，不叫它「完全公開無風險」。URL 與圖片都視為敏感，應遮罩應用／proxy／CDN 日誌、禁止無關追蹤與索引、設定必要 headers、節流及有效期限。
- 媒體有效期要覆蓋實際發訊到取餐期間及允許重試，不可用幾十秒 signed URL 造成顧客稍晚開卡片就是破圖。按既有儲存／LINE 實機行為驗證。
- 規劃媒體 hash 查找與加密 QR payload 的安全渲染；端點只回 image/png，不回訂單 JSON。錯誤／逾期不暴露該人是否存在或私密訂單資訊。
- LINE／裝置可能快取舊圖，顧客也可能截圖；撤銷圖片 URL 不會讓已保存圖片消失。真正安全檢查在服務端 redemption，取消／已核銷／舊版 credential 必須被拒絕。
- QR 的 mediaAccessToken 不能拿去呼叫核銷 API；取餐 credential 也不能呼叫顧客詳情 API。分別測試 purpose confusion。
- iOS／Android 實際聊天室能顯圖、不同亮度能掃，由另一台店員裝置驗證；不要只證明開發瀏覽器看得到。

### 11.5 店員掃描、預覽、確認交付

1. 店員在原後台登入，選定其有權限的實際店家／分店，開啟掃碼入口。相機不可用時提供受控手動查單；支援既有條碼掃描器，不假設 LINE 自带掃碼會直接執行本系統核銷。
2. 取得 QR 後先解析格式，發給授權預覽 endpoint；確認屬於本店、有效、有可交付餐點。未登入或錯店不能查出訂單詳情。
3. 預覽顯示最少核對資訊、餐點、取餐號與付款狀態。現金未結清依原收現程序先確認收款，不把 QR 當作已付證明。
4. 店員實際交付後按「確認交付／完成取餐」，送出 POST，包含 session／CSRF、操作 idempotency key、期望履約版本及 credential。
5. 短交易中檢查權限、付款／履約狀態、未取消、期限及未核銷；唯一一次寫入 pickedUpAt／redeemedBy／device or terminal／來源、更新原履約狀態、消耗 credential 並寫 Outbox。
6. 提交後才推 `ORDER_PICKED_UP`。兩台同時掃、同 key 重試、連點或服務重啟，只有一個交付結果、一個業務通知事件及既有一次計費。
7. 重複掃描回「已於某時間完成取餐」，在授權範圍顯示既有結果，不再做副作用；取消、過期、錯店或未知 token 有清楚不同的安全處理與告警。
8. 不給顧客端一個可直接把訂單設完成的「我已取餐」按鈕。若 repo 既有這類自助機制，需先評估授權與本模式交付語意，不直接拿來發已取餐通知。
9. 不新增無授權的短號公開核銷 API。人工交付須經店員查單、核對、理由與同一核心 command；不因沒有相機就跳過付款或 tenant 檢查。
10. 顧客同時退款／取消與店員掃碼的競態，要以版本及原子約束決定單一可解釋結果；不能已取消卻交付，也不能重複核銷。已交付後退款是另一事件，不重新啟用取餐碼。

### 11.6 上線營運界線

本版一次性核銷代表整單一次交付；若既有產品支援分批取餐，必須顯式區分部分交付與全部交付，只有最後一批完成才發整單「已完成取餐」。不在本次偷偷新增無設計的分批交付模組。

不得透過 client offline cache 在斷線時先寫成成功核銷；伺服器確認前顯示「待確認」，避免兩台離線各發一次餐。正式核銷錯誤需受控更正及稽核，不能刪紀錄當作未發生。

## 12. 商家／平台後台、資料責任與遷移

### 12.1 平台管理者

在現有平台整合設定加入：平台 OA 身分確認、Provider／Channel 對照、MINI App 發布資訊、認證狀態、綁定健康、訊息用量、通知異常與商家啟用名單。

- 只有平台適當角色可替換平台 Messaging Token／Secret、設定 Webhook、發布圖文選單或改平台範本。
- 健康檢查比對真實 bot／Channel 身分與配置，防止測試拿錯 OA Token 而看似發送成功。
- Secret 僅受保護寫入／替換，UI 不回明文或可還原值；記錄版本引用、操作者、時間與理由。
- 平台會員列表／跨店支援需要明確用途、最小權限及查閱稽核，不因 token 屬平台就允許任意員工匯出全部好友。
- 合作店家啟用需要有效服務關係、真實店名／分店／聯絡資訊及授權；不讓陌生租戶利用平台 OA 發未授權內容。

### 12.2 商家管理者與店員

商家只需要開啟「使用攤點通官方帳號交易通知」，填好必要門市資料並管理本店訂單；不需輸入自家 OA ID／Messaging Secret 才能參加。

訂單列表／詳情應顯示製作狀態、取餐號、付款狀態、製作完成按鈕、掃碼確認交付入口、訂單卡／READY／PICKED_UP 的通知紀錄、最新錯誤及受控補發。

權限至少區分：看本店訂單、更新製作、確認交付、人工更正／重發憑證、查看通知狀態、補發通知、申請／核准退款、商家支付設定、平台 OA 管理。一般店員不得改收款主體、讀取平台 Token、選任意收件人或查跨店會員歷史。

### 12.4 Migration 與相容性

- schema、RPC、trigger、view、Realtime、Storage、server privileged queries 一併做授權分析。service role／Prisma bypass RLS 路徑仍須集中式授權與 tenant filter。
- 用複合 FK／唯一鍵或等價短交易約束驗證 order／store／merchant account／credential／event 關係，不只做 UI 檢查。
- 新欄位採相容遷移；舊訂單缺少 LINE 收件映射就安全不發，不猜 identity 或自動歸戶。
- 試點切換定義生效時間與在途事件策略。舊商家 OA 發送狀態未知者先對帳／人工，不把既有通知全部重新送到平台。
- 歷史客戶去重、Provider 不同與資料回填先 dry-run，留可稽核映射，禁止不驗證就合併帳號。
- 只在隔離資料庫驗證，禁止 reset 或 `prisma db push --accept-data-loss`；正式 migration 另列授權關卡。
- 回滾關閉新功能／回復程式，但保留付款、交付、token已核銷與通知證據；不可 destructive down 刪掉外部已發生的事實。

## 13. 資安、隱私與可靠性最低要求

### 13.1 租戶與授權

- Organization／Stall 的授權由經驗證 Session 與伺服器 membership 決定，不採信前端 `organizationId`、`role` 或任意 slug。
- 所有訂單查詢、付款查詢、退款、整合設定與 Realtime 訂閱都測 BOLA／IDOR 與跨租戶存取。
- 開發者測試至少有兩個租戶、兩個同租戶不同店家、兩個顧客與不同角色；以錯誤組合驗證隔離。
- 若使用 Supabase service role 或可 bypass RLS 的 Prisma 連線，不能宣稱 RLS 自動保護它；每條特權資料路徑都要有集中式授權、明確 tenant filter 及負向測試。
- 瀏覽器不能直接修改付款、退款、計費 ledger、Provider 綁定及通知狀態；只允許既有安全的 server command。

### 13.2 Token、網路與輸入

- 輸入 schema、長度／body 上限、rate limit、CSRF、origin、cookie、CORS、CSP 與安全 header 全面依流程驗證。
- 官方 callback／Webhook 按各自協定驗證，不能要求所有入口都帶瀏覽器 CSRF Token，也不能為它們全域關閉 CSRF／Turnstile。
- 若 Cloudflare 防護擋住官方 server callback，只對最小精確路由評估例外，保留協定驗證；不全站停用 WAF。
- 外部圖片、客服網址、付款 URL、deep link 都有可信來源與協定限制。不能拿使用者 URL 讓後端抓取內網或任意攜密鑰請求。
- 接受的 Origin／Callback host 按環境明列；不允許泛用 `*.vercel.app` 帶 credentials、不任意信任 `Host`／`X-Forwarded-Host`。
- HMAC 比對採安全實作；登入與付款交換端點的錯誤回應不暴露帳號是否存在或 Secret 部分值。
- 日誌、Sentry、analytics、traces、CI artifact、HAR、截圖與錄影全部遮罩 Token、Cookie、支付憑證及非必要個資。
- Secret store 與 credential rotation 使用 repo 或平台既有安全能力；無安全管理途徑時，不以明文 DB／前端 env 替代。

### 13.4 監控與失敗處理

至少提供：Request／Confirm／Refund 失敗率與延遲、UNKNOWN 停留時間、對帳差異、過量退款阻擋、Webhook 驗簽失敗、Outbox 堆積、READY 到 Push 首次請求延遲、通知 API 接受率與失敗、平台額度、各店限流、取餐重複／錯店／過期拒絕、跨租戶拒絕、列印結果不明。API 接受率不能命名成顧客送達率。

沿用既有監控，不預設購買新服務。每個告警有可執行 runbook：查詢證據、保留現場、限制新付款、處理 pending、恢復方式。客服看到的是遮罩資訊，不直接取得 Secret。

## 14. Feature Flags、環境隔離與停止開關

以下是設定責任示意，沿用 repo 命名，不製造兩套互相衝突的設定；所有功能由伺服器決定是否可用。

| 責任 | 建議設定／作用域 | 預設與規則 |
|---|---|---|
| 環境 | `APP_DEPLOYMENT_ENV` 或既有機制 | 明確 local／preview／production，不能只靠 NODE_ENV |
| 平台 MINI App | `LINE_MINIAPP_ENABLED`、實際 LIFF ID | 預設關閉新入口，注入該環境實際公開 ID |
| 顧客平台會員整合 | `PLATFORM_LINE_MEMBERSHIP_ENABLED` | 預設關閉新流程，不停用舊登入 |
| 平台 OA 發訊 | `PLATFORM_LINE_OA_NOTIFICATIONS_ENABLED` | 預設 false；平台開關＋試點店白名單＋收件資格 |
| 通知模式 | server registry：`PLATFORM_OA` | 本流程不可切成 merchant OA 或 service message |
| OA 憑證 | 平台 Secret store 引用 | server-only，店員與商家無讀取／任意sender權限 |
| 好友策略 | `REQUIRE_PLATFORM_OA_FRIEND` | 本版預設 true；產品策略，非宣稱 API 無例外 |
| READY／PICKED_UP 通知 | 既有 event policy | 正常流程都啟用，按最新狀態抑制過時事件 |
| QR 核銷 | `LINE_PICKUP_REDEMPTION_ENABLED` | 依店家滾動啟用，不破壞原人工交付 |
| QR 寬限 | `PICKUP_TOKEN_GRACE_MINUTES` | 缺既有政策時建議 120，後台可受控調整，不冒充官方值 |
| Pay 模式 | `LINE_PAY_MODE` | disabled／mock／sandbox／production，缺配置不假成功 |
| Pay 憑證／API版本 | 各 merchant account | 無平台全域 Pay Secret fallback |
| MINI Service Message | 既有 service message 旗標 | 本流程關閉，不作目標 OA 的備援 |
| 測試收件者 | 專用 OA／受限 allowlist | 只准明確指定測試本人，禁止對全好友推播 |
| 新付款停止 | `LINE_PAY_NEW_CHECKOUT_ENABLED` | 與 pending 查詢／恢復分開 |
| 發訊停止 | 平台及各店 kill switch | 阻擋新 Push，不刪除核銷／付款事实 |

- `.env.example` 僅空值／明顯假值，標示公開ID、server secret、平台／商家作用域及必填條件，不把真實 token 放進文件。
- Preview 即使 `NODE_ENV=production` 也不能用正式 Pay／DB寫入或真顧客收件人；fork PR 不取得正式密鑰。
- 優先使用獨立測試 OA；OA Push 沒有可冒充成官方 Sandbox 的假模式，Mock 與真實測試 OA 必須分別標示。非正式 LINE 真訊息測試只在已授權測試帳號／資料下進行。
- MINI App Developing／Review／Published 各自配置合法 ID／audience／Endpoint，與實際 registry 一致。Pay Sandbox 與資料庫隔離都要成立。
- 認證 Review 可能需要固定 HTTPS；沿用暫時性安全 Preview。不得將任意公開 tunnel、localhost 或泛用 `*.vercel.app` 放進正式允許清單。
- 停用新付款時，保留安全的 pending查詢／退款／對帳；停用通知不影響店員履約及本人訂單頁。
- 憑證外洩時停止該憑證所有請求並走事故流程；不為避免中斷持續使用已外洩 Secret。

| F08 | 相同retry key改recipient／body、超24h | 防止變更；超窗未知轉人工，不無限換key |
| F09 | token錯誤、400、5xx、速率429、配額不足 | 分類處理，不一律retry或一律成功 |
| F10 | 200但好友封鎖／無法實際送達 | UI最多標LINE已接受，不偽造已讀／送達 |
| F11 | 平台共用配額、A店大量下單 | 有全局與每店節流、事件優先權及歸因，B店不無限飢餓 |
| F12 | 補發按鈕、同時補發／原worker、已取餐補READY | 權限／冷卻／用途有效，未知先恢復，無重複履約 |
| F13 | 長店名、惡意URL、Emoji、Flex JSON／altText | 正確驗證與安全插值，連結店家正確，無跨店資料 |
| F14 | 首次發卡後狀態更新、取餐QR重發 | 舊bubble標快照，詳情呈現最新狀態，舊QR不可復活 |
| F15 | merchant指定任意to／sender／模板、群組問訂單 | 拒絕濫發與個資外流，商家拿不到平台密鑰 |
| F16 | 通知停用／重啟、舊通道切換／新舊事件交錯 | 核銷與付款不丟；不雙送merchant OA／Service Message |

### G. 必須另列實機端到端證據

至少測 iPhone LINE、Android LINE、一般 Safari／Chrome，加上一台獨立店員掃碼裝置；LINE 桌面只驗證可用的訊息／連結入口。

實機腳本：

1. 測試顧客 A 初次授權、入會、加入平台 OA，從店家 A 深連結下單。
2. 使用合法 LINE Pay Sandbox 測試完整付款、取消、重新返回、關閉重開；標示真實 API 與 Mock 分界。
3. 平台測試 OA 聊天室收到可正常顯示的訂單卡；金額／店名正確，QR可掃，詳情須驗證本人，聯絡為該分店。
4. 顧客關閉 MINI App，店員按製作完成；同一 OA 收到可取餐通知，測量本地事件到首次API請求時間。
5. 店員另一台裝置掃 QR、預覽、確認實際交付；同一 OA 收到已取餐，重掃不得再次成功。
6. 同一顧客在 B 店再下一單，仍是同一平台 OA，店名／Pay收款主體／核銷店家皆正確。
7. 顧客 B 不可讀 A 的卡片詳情；商家 A 不可掃 B 店取餐碼。再測封鎖／解除封鎖、拒絕好友、長文字、暗色／亮色、相機拒權及無網路。

所有結果標示 PASS／FAIL／BLOCKED／NOT_RUN，附日期、裝置／OS／LINE 版本、環境、命令及遮罩後證據。沒有實機、控制台或憑證就標 BLOCKED；Mock、SDK模擬器或瀏覽器錄影不能冒充真實 LINE 推播／Pay／掃碼通過。

## 16. 分階段實作順序

依下列順序分批交付，每批有真實檔案、契約與測試；遵守現行 Skills 必要審閱關卡。不要一開始重做平台首頁，也不要只做到登入就宣稱完成集中通知。

| Phase | 工作 | 應交證據 |
|---|---|---|
| 0 | repo／身分／履約／Pay／通知盤點與官方查核 | 真實路徑、差距表、基線結果及未知外部項 |
| 1 | 平台 Provider／會員／單一OA／各店Pay架構及資料遷移設計 | 短ADR、狀態圖、授權矩陣、相容方案及實際實作計畫 |
| 2 | LINE驗證、平台入會、好友同步、本人跨店訂單及深連結 | A／D組測試，無角色提升或錯誤歸戶 |
| 3 | 既有成立／READY／交付事件＋Outbox＋平台OA adapter | 一條可測的成立→READY→交付通知鏈；真實adapter與Mock分開 |
| 4 | 訂單Flex、QR媒體、店員掃描預覽及唯一核銷 | E／F安全與並行測試，別用裝飾QR交差 |
| 5 | LINE Pay整合／退款／對帳／精度／未知恢復與Billing相容 | B／C金流、故障及既有流程回歸 |
| 6 | 平台管理、商家操作、用量／告警、圖文選單與遷移工具 | 管理權限、dry-run資產、runbook及停止開關 |
| 7 | 實際測試OA／Pay Sandbox／iOS與Android／雙店驗收 | 依第15節逐項結果，修正重大問題後重跑 |
| 8 | 獨立審查、交付、外部設定與認證申請清單 | 真實差異、尚未啟用項、上線及回滾方式 |

可由同一主 Agent 執行，也可依實際工具使用 Identity／Order-Payment／Messaging／Pickup-QR／Security-QA 專職 Agent 接力。共享 schema／狀態機需先定契約再分工；不得多 Agent 同時覆寫同檔，主 Agent 最後跑跨領域驗證。

外部缺項不阻擋獨立可做工作。例如無LINE Pay商家資格仍可完成履約／通知的Mock契約與既有現金回歸；但不能稱Sandbox已過。缺OA Token仍可完成模板、驗簽和去重測試；不能稱顧客已收到。

## 18. 外部設定與正式啟用清單

將缺項集中在同一份 EXTERNAL_SETUP_CHECKLIST；可經已授權工具查到的先查，不請使用者重新提供已存在資料。以下為控制台／商家操作，不代表程式可自動取得認證。

### 18.1 攤點通平台 OA／Provider／MINI App

1. 確認現有「攤點通／QIDAIGO」平台 OA 真實ID、管理者、官方顯示名與現有Bot；沒有就列建立步驟，未獲授權不自行新建。
2. 確認平台合法服務提供者、實際商家／法人資訊及認證OA申請條件；追蹤 `OA verification` 狀態。不能把使用者參考圖的盾牌當成攤點通已認證。[S30]
3. 在 OA Manager 檢查／啟用 Messaging API，先確認 Provider 選擇與既有 LINE Login 一致；不要先建錯Provider再要求搬移。[S27]
4. 確認平台 LINE Login與MINI App歸屬；linked OA固定為平台OA。核對需要的scope、好友選項、callback、region Taiwan、Developing／Review／Published及對應ID。[S02、S24、S25]
5. OA Token／Messaging Secret與Login／MINI／Pay憑證分開存放於server-only secret store。進行遮罩後健康檢查並確認實際發送帳號，不能只看HTTP200。
6. 正確設定Webhook並驗證簽章、destination、重送及空events；先處理舊Bot共存，保留原設定與回復方法。
7. 分別追蹤 Certified Provider 與 Verified MINI App；台灣認證資格依當日官方要求。普通平台OA Push的完成驗收不能拿「還沒有Service Message模板」當作未做的理由。[S02、S04]
8. 準備平台品牌圖、真實隱私／會員條款／退款／客服資料；對外資訊如有缺少就阻擋相關公開項，不編造法人。
9. 經測試與授權後才發布平台圖文選單與歡迎訊息。記錄當前OA訊息方案及配額；不自動加購或升級。[S17、S29]

### 18.2 各合作店家

1. 確認合作授權、店家／分店識別、地址／取餐位置、電話、營業及取餐時間、履約操作員權限。
2. 啟用平台OA通知策略與本店取餐流程；不需要商家先開一個自己的OA。
3. 確認該店 LINE Pay 線上商家資格、API版、正式收款名稱、退款能力及憑證，資料留在原有安全管理。
4. 在隔離環境完成Sandbox付款、取消、查詢、退款與故障恢復；真實小額交易／退款須另有明確授權。
5. 設定／確認取餐碼期限與延遲處理政策、店員掃碼設備及無相機備援；現場演練製作完成→顧客通知→掃碼交付。
6. 分批啟用試點A與第二家測試店；確認是同一平台OA，但各店各自收款與資料隔離。

## 19. 最終驗收、回覆與上線關卡

### 19.1 不得省略的業務驗收

- [ ] v2模式已實作：多家合作店的主要交易通知，都由同一「攤點通平台OA」發送。
- [ ] 合作店家不需提供自己的Messaging Token；平台Token不暴露給店家。
- [ ] LINE驗證／平台入會／好友／行銷分開；沒有新密碼登入或錯誤員工角色。
- [ ] 顧客本人可查跨店訂單，商家只能讀自己的店；他人／跨店負向測試通過。
- [ ] 一筆正常有效訂單依真實階段完成卡片→可取餐→已取餐，資料及sender正確。
- [ ] 店員有明確製作完成入口，KDS與非KDS都能觸發；不靠預估時間／付款冒充。
- [ ] QR在真實LINE卡片可顯示、可由店員裝置掃描；不是裝飾圖。
- [ ] 掃碼預覽不直接核銷；店員確認實際交付才唯一完成，重掃／跨店／過期／取消都安全。
- [ ] Pay是原正確商家收款，非平台OA統收；金額、長交易ID、簽章、重試、UNKNOWN與退款完整。
- [ ] 通知失敗不回滾履約，API接受不冒充已讀；LINE回應不明可用相同retry key恢復。
- [ ] 不雙送商家OA或MINI App Service Message，不把它們當平台OA的替代驗收。
- [ ] 平台配額、每店歸因、節流、人工補發、stop switch與對帳／復原已可操作。
- [ ] 原Web／QR／訪客／Google／LINE／Apple、POS／KDS／印單／既有完成單計費沒有退化。
- [ ] iPhone、Android、獨立店員裝置與至少雙店測試有真實證據，或清楚列BLOCKED不得公開稱完成。
- [ ] 正式安全、商家Pay資格、需用的OA／MINI設定與期望的認證狀態已核對；未取得前不冒認。
- [ ] 正式啟用或真顧客發訊有授權，且沒有把Preview／Mock／Sandbox當Production。

### 19.2 最後分開回報，不能一句「全部完成」

| 層級 | 必須回報 |
|---|---|
| Code | 真實修改檔案、已完成／未完成能力、與既有核心的對接 |
| Automated tests | 命令、退出碼、通過／失敗／跳過數及失敗真因 |
| Real OA／Pay Sandbox／Device | 用哪個隔離環境與測試帳號、sender核對、實機QR及訊息證據；缺項標BLOCKED |
| External approvals | OA認證、Provider／MINI認證、Pay商家資格與外部設定各自狀態 |
| Production | 未啟用／待申請／待設定／經授權已啟用並驗證，實際做過哪些外部變更 |

最後用繁體中文給：完成範圍、關鍵路徑、相容性、測試證據、外部設定清單、店員操作入口、上線／回滾、剩餘風險。只交文件或Mock時，不能說「顧客已可在平台LINE收到通知」。

**開始執行時：先做 Phase 0 的真實盤點。遵守必要審閱與授權關卡，然後依各階段持續完成可自主工作；帳號、憑證與官方申請缺項集中交付，不把這些缺項當作不寫核心程式或不測試的理由。**
