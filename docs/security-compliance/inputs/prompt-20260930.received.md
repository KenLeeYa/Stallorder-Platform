## 2026-09-30 架構校正與執行優先規則（v2.0）

本節是本版的最新業務契約；原文若寫「平台單一 LINE OA 已為現行通知模式」，以本節取代。2026-09-29 安全評估中描述的平台單一 OA 是先前規格，不能因此認定已實作、已啟用或仍為近期發訊方案。每一項仍須由當前 repository、環境與商家實際設定驗證。

| 能力 | 現階段目標 | 未來保留能力 | 狀態判定 |
|---|---|---|---|
| LINE 訂單與取餐通知 | **各合作商家以自身 LINE 官方帳號發訊**；攤點通共用後端接收、驗證、排程、發送及狀態核對 | 平台管理者可按安全遷移方案切換至平台 OA 發訊 | 需求，須查程式及各店設定 |
| OA Webhook | 平台後台集中管理各店 Webhook URL：讀取遠端、測試、套用、比對遠端與本機狀態 | 平台 OA 可走相同受控管理介面 | 需求，非已完成證據 |
| LINE MINI App／Mini Store | 商家可獨立選擇是否啟用，依實際 LINE 渠道與資格綁定 | 支援日後平台入口與多店體驗 | 需求，不能與通知綁死 |
| LINE Pay | 各店自行選擇、以各店簽約的商戶收款；和 OA／Mini Store 開關分離 | 擴充其他合規支付方式 | 不得推定已取得正式資格 |
| 第三方 OMO／POS、共餐、配送 | 對保留既有系統的商家提供授權介接契約；新模式依實際 Phase 導入 | 跨系統聚合、透明運費及供應鏈 | 未實作能力只建安全邊界 |

核心設計為「通知 sender／provider 的受控選擇」，且切換模式不重建訂單、顧客、支付或同意資料。帳號身分、好友關係與 LINE user ID 必須按 provider、channel、subject、目的和授權範圍建模；**不同 OA／Login channel 的 user ID 不可當成相同主體或任意互換**。從各店 OA 改為平台 OA 前，盤點加好友／收件資格、告知與同意、渠道識別映射、訊息額度、過渡雙發及失敗回復。禁止為了節省額度而繞過收件資格或跨店發訊。

本版依據：同名 2026-09-29 安全評估、OMO／SCM v2、Agency Agents 接力 Prompt，以及 2026-09-29 的各店 OA 最新管理需求。它們是架構輸入，不是 code audit；真正的現況以固定 HEAD、設定及測試證據為準。法律生效日期、LINE／支付平台規則與 SDK 版本必須在執行當日查官方來源。若來源不能取得，列 BLOCKED／NEEDS_LEGAL_REVIEW，不能沿用舊日期宣稱已核定。

### LINE OA 與商家選配模組的必要實作契約

1. 建立商家／門市與 OA channel 的明確綁定及狀態機；區分 Login、Messaging、MINI App 與 LINE Pay 的 channel、secret、token 和 merchant credential。敏感設定用秘密管理儲存，UI 僅顯示遮蔽識別、版本、狀態與輪替資訊；商家和平台支援人員不得讀回明文。
2. Webhook 以該 channel 的 secret 驗證**未修改的 raw body**與簽章，再核對 destination／商家綁定、事件 ID 冪等、時間與重放策略。不得用 URL path 或未驗簽 body 自稱商家。重複、錯 channel、已停用 channel 與跨店事件要安全拒絕且不更新訂單。
3. 平台後台遠端讀取、測試、套用 Webhook URL 必須走伺服器端供應商 API 與最小權限憑證；測試與套用分離，套用前再驗證當前版本與目標環境。紀錄操作者、商家、遮蔽差異、遠端回應、版本與時間；錯誤時不得把本機狀態冒充遠端成功。對 URL 設精確允許範圍及 SSRF 防護，不能把管理介面當任意 URL 探測器。
4. 通知 Outbox 將 order、stall、channel、sender、recipient、template version、consent／service-purpose、delivery attempt、provider response 綁定；worker 送出前重新核對店家及收件資格、開關、sender 版本、訂單狀態、退訂與撤權。服務型訂單通知與行銷目的分開；沒有收件資格則提供站內查單／商家作業補救，不影響交易真相。
5. 商家獨立設定 OA 通知、Mini Store、LINE Pay，開關和授權可單獨撤銷。關閉其中一項不得破壞其他兩項或既有訂單。每店額度／節流及平台整體保護、訊息模板最小個資、重送冪等和 provider 失敗狀態需有可見證據；HTTP 接受不等於已送達或顧客已閱讀。
6. LINE Pay 的商家憑證、PaymentAttempt、金額／幣別／環境、退款和對帳獨立於 OA Webhook。前端 return 不是付款證明；未知結果查詢後才推進狀態。不得以 OA 簽章驗證 Pay，不得將 A 店款項導向 B 店 merchant。
7. 預留 `sender_mode = MERCHANT_OA | PLATFORM_OA` 之類的受控策略，並提供不可同時雙發的切換與回退檢查。資料 migration 採 additive；每筆事件保留當時 sender 與收件渠道，不追溯改寫歷史訊息與同意。
8. 取餐 QR、顧客訂單卡、掃碼核銷與付款／交付為各自授權事件。掃碼 GET 僅預覽，員工確認 POST 再查店、角色、狀態及版本並原子核銷；QR 洩漏不可取得付款、退款或跨店權限。
9. OMO／SCM 的買賣企業、承運者、批次與庫存、ePOD、離線裝置及第三方 POS 各有 scope。只共享授權交易的必要欄位；GPS、照片／簽名和配送地址依任務存取及保存；重派或撤權後離線補傳須重新授權。來源系統訂單 ID 不能作跨平台唯一鍵。
10. 已存在的部署與功能先查證並重用；尚未存在的 LINE、OMO 或配送 Phase 不因本安全任務被宣稱完成，也不為了填表擴大成完整產品開發。與本次安全控制直接相關的程式、migration、測試及文檔要做到可執行，不只生成規格。

3. 先完成本機程式、合成資料驗證、文件、dry-run、差異與復原計畫。缺外部設定只阻塞相關整合，繼續其他可做工作。

7. 長任務保存可續跑狀態；不要在一個 Phase 完成後停住。遇阻塞寫原因、可重現證據與下一步，完成所有可獨立進行的工作。

## 3. 威脅模型、資料角色與最小蒐集

### 3.1 必須畫出的資料流

建立現況與目標 Mermaid 圖，至少涵蓋：顧客、商家員工、平台管理員、供應商、POS／KDS、印表機、Web／App、API／Edge、Auth、Prisma／Postgres、Storage、Realtime、queue／cron、支付與外送／物流／通知、稽核、CI、備份與 DR。

每條跨界資料流記錄發起者、身分、租戶／門市、合法目的、資料分類、傳輸區域、授權點、加密、保存、第三方與失敗行為。以 STRIDE 加個資威脅檢查冒名、越權、竄改、抵賴、洩漏、阻斷、關聯識別及目的外利用。

### 3.2 角色與資料責任

- 商家因履約／會員用途決定顧客資料使用；平台提供受託處理服務時有相應義務。
- 平台為自身帳號管理、計費、資安或防詐自行決定用途的部分，獨立列出告知與合法依據。
- 支付、外送、雲端或通知供應商的角色依契約與實際使用判定，不統一假設全部是同一種受託者。
- 台灣法用語與 GDPR 的 controller／processor 不混為相同法定概念；在適用 GDPR 時再建立對應。
- 平台登入 identity、商家 Customer、供應商 TradingRelationship 與行銷 Consent 分開。相同電話或 Email 不代表可跨店／跨企業自動合併或共享。
- 美業若有病歷、醫療等敏感欄位，另外盤點個資法第 6 條等適用條件；一般食物偏好不自動等同醫療資料，具體內容按實際性質判斷。

### 3.3 資料盤點

盤點欄位包括姓名、電話、地址、Email、OAuth subject、LINE channel scope、裝置識別、IP、訂單與付款 reference、餐點備註、員工紀錄、供應商聯絡人、發票載具、匯出、日誌及備份。每項記錄目的、必要性、法律依據、可見角色、資料所在區域、保存與刪除策略。

餐飲訪客下單保留；不要求無關的身分證、完整生日、聯絡人或背景定位。不從 OAuth 取得下單不需要的 scope。不以一般服務條款代替所有目的的個資同意。

## 4. 身分、Session、管理權限

1. OAuth/OIDC 依各 provider 官方流程驗證 issuer、audience、signature、expiry、state／nonce 及適用的 PKCE。Server 驗證登入結果，不信任前端回傳的 user ID／Email。
2. redirect URI、return URL 與 App deep link 採精確允許清單；Production 不使用任意 Preview wildcard，不允許 open redirect。
3. 帳號連結需驗證既有身分與新 provider 的控制權並防 CSRF；Email 一樣、Apple relay Email 或 LINE 不同 channel subject 不作自動合併依據。
4. 不用可由使用者修改的 user_metadata 作為角色、tenant 或 entitlement 依據。若使用可信 JWT claims，仍處理 claims 過期與撤權一致性。
5. session／refresh token 依既有架構安全處理。Web BFF cookies 使用合適的 Secure、HttpOnly、SameSite 與 host scope；若瀏覽器直接用 Supabase session，不破壞 SDK 契約硬套 HttpOnly，應記錄風險與遷移方案。
6. 管理員強制使用已成熟且可驗證的第二因素；保留 Google／LINE／Apple 主登入。原生支援不足時採相容的安全 MFA 實作，不能把存在未驗證 Beta 功能當作已完成。
7. 退款、敏感匯出、管理權限、收款資訊、金鑰發放、租戶轉移與帳戶刪除需近期驗證／step-up；驗證的新鮮度綁 session、操作類型與必要內容，不只檢查前端按鈕。
8. 刪除 user 不代表已簽發 JWT 立即失效。敏感操作需檢查停權／session 撤銷／會員有效性；實作可驗證的撤銷策略，不只縮短 token TTL。
9. 裝置與 session 可查看及撤銷；離職／角色變更使敏感權限於後續請求失效，queue 與長連線也需處理。
10. 客服支援採限時、指定租戶／目的的授權，預設唯讀與遮蔽；保留真實操作者及代理對象，不共用帳號、不交換商家密碼。
11. 高影響操作能支援發起／核准分離。若實際只有一位負責人，不能捏造第二核准者：保留重新驗證、完整內容確認、不可任意刪除的證據及明確單人殘餘風險。
12. 帳戶恢復不得比正常登入更弱；MFA 恢復、擁有者轉移與最後一位 owner 刪除要有可驗證流程，防止自我升權與社工。

## 5. 多租戶、Prisma、RLS 與欄位授權

### 5.1 統一授權決策

將 `actor + active membership + organization + stall scope + action + resource + entitlement + context` 放在伺服器可信授權路徑。前端傳來的 tenant／stall 只能是待驗證輸入。每個讀寫、Server Action、RPC、export、Realtime 與後台工作都要有實際保護。

- UI 隱藏不等於授權；entitlement 不取代 actor permission，permission 也不取代 tenant 隔離。
- 授權通常為必要條件的交集；合法 OR 只用於明確替代角色，不得把「有訂閱」當全租戶可讀。
- 租戶與門市條件不可被搜尋、分頁、日期、排序、object spread 或 filter merge 蓋掉。
- 直接讀資料表、REST、GraphQL、Edge、view、RPC、Storage、Realtime 與原始部署 URL 都要測；CORS／Origin 不是身分驗證。
- 平台管理員、商家 owner／manager／cashier／kitchen、供應商、auditor、service worker 採能力與範圍最小化；auditor 預設遮蔽及唯讀，沒有操作權。

### 5.2 PostgreSQL 與 Prisma 執行角色

盤點實際 connection role、owner、GRANT、role inheritance、BYPASSRLS、schema exposure、RLS policy 與 transaction pooling 行為。Supabase service role、Postgres superuser／BYPASSRLS、通常的 table owner 可繞過 RLS；FORCE RLS 也不會約束 superuser／BYPASSRLS。[PostgreSQL 官方說明](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)。

一般應用資料存取逐步使用受限執行角色；migration／管理角色與 runtime 分開。既有受信任 Prisma DAL 仍必須顯式做租戶與資源授權。若當前 Prisma 使用特權角色，不得只加 RLS 就宣告完成：需修正角色及安全 context，或在短期兼容方案中保留明確殘餘風險與發布限制。

採 transaction-local tenant context 時，必須由可信伺服器產生，在同一 transaction／connection 設定並執行；處理連線池、並發請求與 rollback，不讓上一位租戶 context 流入下一個請求。不把可由客戶任意設定的 session variable 視為完整授權。

### 5.3 RLS／SQL 物件

- exposed schema 的每張表逐項設定最小 GRANT 與 RLS。匿名僅可讀明確 public projection，不能開啟泛用訂單讀寫。
- 分別驗證 SELECT、INSERT、UPDATE、DELETE；UPDATE 明確列 USING／WITH CHECK 的原列與新列約束，並檢查搭配 SELECT 的需求。
- 檢查寬鬆 policy 的 OR 效果；不能因新增更嚴格 policy 就假設舊寬鬆 policy 不再有效。
- view、materialized view 與聚合資料各自審查。適用版本下普通 view 使用 security_invoker；不支援時限制 schema／GRANT。materialized view 不直接套普通 view 方案。
- SECURITY DEFINER 僅限必要範圍，固定 search_path、完整限定物件、限制 EXECUTE 與呼叫者／租戶／輸入，不為通過測試任意加上特權。
- background RPC 的 service identity 與使用者 RPC 分開；不強迫所有 worker 都假裝有 end-user auth.uid，也不允許 service 身分走無限制的 public RPC。
- 寫入資料的 organization／stall 由可信資料關係約束；跨租戶 FK、連結表、更新 ownership 與 unique scope 都要檢查。不得只在 insert 前查一次而缺少 transaction／DB 約束。
- runtime role 不授予 DDL、TRUNCATE 或 role management。測試角色與 migration role 分離。

### 5.4 供應商共享與欄位保護

買方 PurchaseOrder 與賣方 SalesOrder 各屬原組織；只透過受限關聯與 DTO 共享交易必要欄位。建立／撤銷合作關係不會自動開放歷史資料、全部顧客、供應成本或其他買方交易。

需要保留的售後／帳務資料與新的業務資料分享分開。VMI 只共享核准庫存摘要。員工可看菜單不代表可看成本，可履約不代表可匯出顧客，能看報表不代表能發行銷。

## 6. 個資中心、告知、同意、保存與刪除

### 6.1 可使用的介面及事件

實作顧客與商家可操作的個資／隱私入口，以及管理端處理工作台。沿用現有 UI，不在顧客流程顯示資料庫名稱、policy ID 或內部錯誤。

至少支援：告知內容、版本及聯絡方式；資料查詢／閱覽／複製；更正；停止處理或利用；刪除申請；行銷偏好及撤回；受理状态、期限與結果說明。訪客有安全申請方式，不為申請資料而強制註冊。

將 privacy notice、service terms、必要履約依據、行銷 consent 及 App 裝置權限分開。行銷採清楚獨立選擇、預設不勾；記錄目的、渠道、租戶、版本、時間、取得方式及撤回。發送時重新確認，已排隊未發送的行銷也能停止。交易通知不得夾帶推銷來規避退訂。

### 6.2 權利請求與期限

建立 `requested_at / verified_at / request_type / legal_rule_version / decision_due_at / extension_reason / notified_at / execution_status`。依個資法第 13 條分別處理 15 日或 30 日准駁及相應延長，不套用一律 30 日；書面延長／拒絕理由可產出並保留。身分補正與法定起算方式須有法律依據，不可自行暫停法律時鐘。[個資法有效條文](https://law.moj.gov.tw/LawClass/LawOldVer.aspx?pcode=I0050021)。

身分核對依風險使用既有登入／訂單控制權等方式；不普遍索取身分證影本。防止假冒刪除、資料匯出送錯對象或包含其他家人的帳戶。逾期提醒、補正、拒絕、部分準許與再次處理均有 audit。

### 6.3 Retention policy engine

沿用既有政策模組，必要時建立版本化資料保存策略，欄位包含資料分類、目的、法律依據、起算事件、期限、例外、保全、刪除方式、責任人及核定狀態。區分法定最低保存、業務合理必要與工程暫存。

- 依安維辦法第 16 條評估必要軌跡／安維證據的至少五年保存；不能把所有 log 都設 30／90 日後清除。
- 會計憑證原則五年、會計帳簿及財報十年，其起算及例外依商業會計法第 38 條與會計審查；不要由此推導所有顧客資料留十年。
- 訂單聯絡資訊、自由文字、會員、行銷、通知、匯出、列印、資安監測與備份各別規則；一欄需要保存不代表整筆資料全部保存。
- 尚無核定期限時產出草案及 dry-run，不啟動不可逆刪除；新資料維持最小化，該政策尚未完成需留在 readiness 缺口。
- 工程起始值可採匯出／已完成列印內容 24 小時、非必要 debug 14–30 日，均標明內部建議；不得覆蓋依法應保留的事件。
- 法律保全 `legal_hold` 要有範圍、理由、到期檢查、權限與解除紀錄；不可成為無期限保留全庫的開關。

### 6.4 刪除、匿名化與還原

刪除工作涵蓋主庫、讀副本、Storage、cache、搜尋索引、queue、通知／匯出檔、分析資料及合理範圍的受託者協作。交易必要資料與可移除個資分層，帳本以去識別或受限關聯保存，不破壞法定帳務、退款與未結爭議。

記錄最小刪除 tombstone／處理清單，限制其用途與保存。備份不能逐筆即時改寫時，明確記錄淘汰期限、限制存取，還原後在開放服務前重套刪除、停權與撤銷，不让資料復活。

匿名化與假名化明確區分：可還原的加密、普通電話 hash 或可連結 ID 仍需當個資管理。不得在 audit 的 before/after、錯誤追蹤或 SQL log 保留剛刪除的完整資料。

## 7. 金鑰、加密、檔案、快取與資料外洩

1. 盤點 secret 的用途、持有人、環境、權限、到期、輪替與撤銷。輸出只含名稱／安全指紋與設定狀態，禁止輸出 .env、process.env、token、cookie、連線字串或完整支付 payload。
2. service_role／DB 管理金鑰不得進 NEXT_PUBLIC、瀏覽器 bundle、source map、App、印表機、前端 log 或公開 repository；publishable key 本身不視為授權秘密，但不能取代 RLS。
3. Transport 使用可用且安全的 TLS，驗證憑證。資料庫傳輸與靜態加密逐项查設定，不僅以供應商宣傳頁當環境證據。
4. 對高敏感聯絡資訊、外部 access token、收款設定等評估欄位加密，採成熟 AEAD 與金鑰版本／nonce 管理；tenant、欄位／記錄綁入必要 AAD。不得自創加密算法。
5. 不可逆設備 token 採高熵生成並安全驗證 hash；需送外部 API 的秘密採加密，不能因只存 hash 而使功能無法運作。輪替包含並發中的合法工作、有限交接期與明確撤銷。
6. 如需電話精確搜尋，使用可信 secret 的租戶範圍 HMAC／blind index 並限制查詢；不得用可枚舉的普通 SHA256 號碼作匿名化。處理 normalization、key version 與遷移。
7. Storage 的顧客、報表、合約、發票及上傳原檔預設 private。公開菜單與商品圖只允許審查後的公開投影／資產，避免把所有產品圖片改 private 造成既有 URL 損壞。
8. uploads 控制 MIME／magic bytes、大小、像素、解壓上限、檔名及路徑；對危險格式隔離、重新編碼或拒絕；清除不必要 EXIF。依格式與風險使用掃描，失敗不得默認發布。
9. 敏感匯出使用下載時重新授權的受控路徑或可立即撤銷機制；普通 presigned URL 在有效期內未必可撤銷，不可虛稱撤權後必然即時失效。限制有效期、下載數與快取，必要時用受保護代理下載。
10. CSV／Excel 輸出防公式注入；標準換行、引號與 delimiter 編碼；匯入拒絕 mass assignment 與超額批次，先 dry-run 再 transaction。
11. 個資回應、帶 session 的頁面與匯出不進共用 CDN cache。公開 tenant cache 的 key 包含可信 host／tenant／版本，避免跨店與草稿洩漏；request memoization、ISR／RSC、Redis、Service Worker、IndexedDB 也要檢查。
12. App crash、APM、session replay、analytics、URL／Referrer、瀏覽器 history 與第三方 script 均納入洩漏盤點；token 不入 query string，若既有協議無法避免，做最小有效期、日誌遮蔽與遷移。

## 8. API、Edge、代理信任與防濫用

### 8.1 應用安全

- 所有輸入在可信後端做 schema／長度／範圍／enum 驗證；價格、折扣、稅金、庫存、營業時間、停售、訂單狀態與費率由 server 計算。
- 防止 SQL injection、stored／reflected XSS、template injection、命令注入、path traversal、open redirect、不安全反序列化與 mass assignment；沿用成熟函式庫。
- cookies 授權的狀態變更處理 CSRF；採正確 Origin／CSRF token 等措施，不能用全域 CORS wildcard 加 credentials。
- CSP 先盤點實際支付、OAuth 與 Star 列印需求再逐步收斂。nonce／hash、frame-ancestors、nosniff、Referrer-Policy、Permissions-Policy 與 HSTS 按路由及網域實際支援設定；不一次開 preload／includeSubDomains 導致舊門市終端失效。
- 錯誤回應只給安全訊息與 correlation ID，內部詳細 stack／SQL 留在遮蔽、受限的記錄。

### 8.2 入口不能繞過安全控制

逐項列出 Cloudflare（若實際使用）、Vercel 原始網域、custom domains、Supabase URL、Data API、Edge、Storage、Realtime、cron 與 internal endpoints。每條公開可達路徑都有獨立授權與濫用控制，不把 WAF 有開視為完成。

僅在已證實的受信任 proxy chain 接受 forwarded IP／host／proto；測試直接呼叫時偽造 X-Forwarded-For／Origin 等標頭不會取得特權或繞過限流。供應商簽章與 session／capability 才是授權依據之一；IP／Origin 只能作相應輔助。

### 8.3 受控外連及 SSRF

支付、列印、webhook、匯入、圖片抓取與網站 metadata URL 皆需正規化與精確協定／host／port 限制。處理 redirect、DNS 重綁、IPv6／IPv4 變形、loopback、link-local、私網與雲端 metadata；每次轉址重新驗證或禁用轉址。雲端 worker 不可任意探測商家內網；明確授權的門市列印由限定功能的本機 adapter／device 通道處理。

### 8.4 假單、資源與成本

採分散式限流與配額，按 endpoint、tenant、actor、可信裝置、IP／network 多種因素控制，避免全店共用 NAT 被一人拖垮。限制匿名查單／取餐碼、報表時間範圍、匯出筆數、圖檔／儲存量、queue depth、重試、通知、AI token 與第三方 API 花費。

Turnstile／CAPTCHA 應在 server 驗證，支援合理替代流程；不能作為唯一安全邊界。防重播、優惠反覆領取、假退款、惡意大量取消、重複完成與供應商批次濫用。不單憑不穩定 IP／裝置指紋永久封鎖合法使用者。

依風險定義故障行為：權限、付款、匯出與管理操作在驗證依賴失效時拒絕；公開菜單可使用已核定的公開快取；一般訂單如允許降級也必須保留冪等、資料驗證與配額。不可把所有服務一刀切停止，也不可對高風險功能 fail-open。

## 9. 支付、退款、庫存、點數與計費安全

1. 每個 adapter 依該 provider 正式文件實作簽章／MAC、原始 body、時間／nonce、key version 與安全比較；不同 provider 不硬套同一驗簽演算法或不存在的 timestamp 欄位。
2. 支付回調必須比對 provider、環境、merchant account、訂單、金額、幣別、事件類型與允許狀態。IP allowlist 不能代替驗簽；provider 沒有可驗證 webhook 時以官方查單等方式確認，不能信任瀏覽器成功頁。
3. `environment + provider + merchant account + event/transaction/operation identity` 定義正確冪等範圍，資料庫 unique constraint 與 transaction 落實；不可只用記憶體 Set、前端按鈕 disabled 或單一 Redis TTL。
4. 同 idempotency key 的不同 payload 必須拒絕衝突；相同請求返回已存在的合法結果。記錄安全摘要，不能保存整份卡片／憑證資料做去重。
5. 事件 durable 入 Inbox／Outbox 後才按 provider 契約回覆成功；先 ACK 再依賴易失性記憶體工作不可接受。重播與 DLQ 重跑保留原 operation identity。
6. 網路逾時不是扣款失敗。模糊狀態先查詢／對帳再決定，不能重新建立新扣款；處理亂序與重複 webhook、退款與付款同時到達、部分退款及退款總額上限。
7. 收款資訊、結算帳戶、退款目的地或 provider credential 變更需 step-up、適用的核准與通知草稿／受控流程；不接受客戶端任意指定退款收款人。
8. 支付、商家收現金確認、列印、開櫃、交付與訂單完成為不同事件；不得因印單成功或支付頁 redirect 就標 completed。
9. 庫存保留與釋放、組合品／加料與贈品、停售／召回、點數及優惠預算在可信交易範圍原子校驗；重送只作用一次，最後一件商品不超賣。
10. 供應商 PO、SO、ASN、收貨、退貨、調撥與 AP／AR 不得冒充 B2C completed 事件產生平台費；不同通路 mirror 對應同一 canonical order。
11. PAYG 沿用 usage ledger／PlanVersion，事件到達時間與計費 business time 分開；Asia/Taipei 月界、退款折抵、含稅上限與關帳策略以現有有效契約實作，缺定義列 gate。
12. 管理員調整以 reversal／credit／debit 等經核定事件處理，不覆寫已入帳帳本。對帳異常有可操作待處理隊列，不靠 clamp 成零掩蓋差異。
13. LINE Pay、台灣 Pay、街口、全支付與其他 provider 的實際支援按各自官方規格／收單合約確認。不得因品牌屬於某支付生態就宣稱單一 API 全部支援。
14. foodpanda／Uber Eats 事件與資料按正式授權範圍使用，處理接單狀態、資料保存及重送；沒有商用資格或正式測試就記 BLOCKED，不使用假成功 adapter 上線。

## 10. POS、列印、錢櫃與離線安全

### 10.1 硬體身分與工作

- 每個 device 綁 organization、stall、類型與允許操作，具備註冊、核准、停用、輪替、最後使用與安全狀態。
- 印表機只能 poll／claim／download／ack 它被分配的工作，不能查全店任意歷史訂單；token hash 管理表不對一般 authenticated 開放。
- 合法工作在輪替期間按明確協議完成；過期憑證不得建立新工作。避免無限寬限期，測試併發 poll／ack 與輪替。
- CloudPRNT 使用穩定核准的 HTTPS endpoint，不把隨機 Preview host 當正式輪詢目的地。除錯紀錄與打印內容不含秘密。
- PrintJob 的冪等、claim lease、ack、重試與重新列印分開。網路 ACK 遺失時可能無法保證紙張只印一次，需標示重印／待確認並提供人工處理，不能宣稱跨硬體 exactly-once。
- 訂單內容依廚房、收銀與外送需要最小化；紙本不印完整電話／地址，除非對應履約需要。逾期工作 payload 清除，必要操作證據另外保存。
- 手動開錢櫃有獨立權限、理由、操作者與事件；支付通知、重印或匿名下單不能直接開櫃。
- 不因藍牙／webPRNT 共用就假定多台平板可同時佔用同一硬體；實機驗收與模擬驗收分開。

### 10.2 門市與離線

- 建議訪客 Wi-Fi 與 POS／印表機分段；設備更新、預設管理憑證、配對與停用有 runbook，避免向公網開放印表機埠。
- 原生 App 祕密使用 OS Keychain／Keystore；Web 的 localStorage／IndexedDB 不具同等隔離，不能把同源 JS 可取得的加密 key 當成抵禦 XSS 的保證。
- 離線優先保留最少必要資料及草稿；若既有允許受控離線現金交易，沿用範圍、配額與 operator／device 身分。離線不授權敏感匯出、退款、升權或確認線上支付成功。
- 同步使用穩定 operation ID、原始門市與裝置版本；重新驗證價格／庫存／權限與交易衝突，衝突不能靜默改寫原交易。
- 多分頁、App 重開、網路斷續、裝置撤銷與換店要測。登出／換租戶先封鎖舊資料顯示；未同步交易由有權者安全處理，不默默刪除或送往新租戶。
- 切換 session 後清除／隔離舊快取與 service worker response；推播預設不含完整個資，只在重新登入授權後開啟詳情。
- deep link、WebView bridge 與 PassPRNT 參數採最小功能和來源限制，不能提供任意 URL／JavaScript／檔案／shell 執行通道。

## 11. 稽核事件、完整性與監控

### 11.1 Audit event 的最低結構

沿用既有 audit 模組，增加必要欄位而不重建衝突的稽核系統：

```text
event_id / schema_version / occurred_at_utc / recorded_at_utc
actor_type / actor_id_or_pseudonym / effective_actor / session_or_device_ref
organization_id / stall_id / action / resource_type / resource_id
decision: ALLOW | DENY | ERROR / safe_reason_code
request_id / trace_id / operation_id / idempotency_ref
changed_field_names / redacted_change_summary
approval_ref / legal_purpose_or_case_ref
policy_version / environment_id / release_sha
integrity_batch_ref / retention_class
```

不能把前端送入的 actor／tenant／occurred_at 全盤當真；對不可信裝置時間保留來源時間與 server 接收時間。不要記錄完整密碼、token、cookie、卡片資料、姓名電話地址或任意 before/after 快照。需比對變更時使用安全摘要與受限資料引用。

### 11.2 必須有事件的操作

登入及驗證異常、帳號連結／恢復、權限／entitlement／owner 變更、客服代理、敏感資料查看／批次查詢／匯出、個資請求／刪除／保全、退款／計費／庫存調整、收款資料異動、憑證發放／輪替、PrintJob／開櫃、供應商共享、策略變更、重要拒絕、migration／發布、備份／還原／DR 切換與必要封存驗證。

公開菜單等低風險流量不必逐筆保存個資，依必要性採聚合。依法需保存的軌跡不得用 sampling 丟棄；audit 與一般 telemetry 的保存類別明確分開。

### 11.3 原子性與防竄改

- 寫入業務事件與必要 audit／Outbox 同 transaction；持久化失敗時不能提交未留證據的高風險業務操作。
- 敏感讀取／匯出若無法記錄必要證據，拒絕交付資料或使用已核定可持久化的安全降級路徑。對外封存服務暫停時可使用容量受控的持久化 outbox，不能全面因遠端日誌短暫故障停單。
- 普通 runtime 不具任意 UPDATE／DELETE audit 的能力；維護／retention job 限定角色與範圍，刪除本身有事件及核准。
- 使用穩定序列／分區策略、簽章 manifest 或 hash chain 做完整性驗證，支援補遲事件、順序差異及缺號偵測。
- 同一資料庫管理員若能重寫資料和 hash，就不具獨立防竄改能力。長期證據需要分離管理權的封存目的地或適合的 WORM／Object Lock 能力，並可驗證簽章和存取紀錄；能力未取得時列明限制，不能將一般 private bucket 稱為 WORM。
- 只在經核定後啟用不可逆 retention lock，先準備範圍、成本、期限與測試結果，避免把含個資的錯誤 payload 永久鎖住。

### 11.4 偵測與營運儀表

建立跨租戶拒絕暴增、異常匯出、管理員新裝置與提權、金鑰使用異常、webhook 驗證失敗、支付對帳差異、重複工作、DR lag、writer 衝突、稽核封存延遲、資料刪除失敗、備份過期、成本與容量超限的規則。

每條規則有 owner、範圍、閾值、抑制／去重、處置、runbook 與測試事件。若通知渠道未設定，仍可使用工作台／本機測試 sink，標示外部告警未驗證；不要在本次開發自動聯絡真實顧客或主管機關。

## 12. 資安治理、事故應變與法務責任

### 12.1 必須有的管理機制

建立可維護的資產／資料／供應商／風險登錄，指定資安、個資、事件、發布、帳務及客服負責角色；未提供姓名使用待指派欄位，不虛構人員。

風險列影響、可能性、控制、負責人、期限、驗收、殘餘風險及接受權限。新增權限、人員離職、外包帳號與設備回收有流程。重要特權定期複核；訓練與商家個資守則有版本與實施紀錄。沒有辦過的稽核／演練／訓練不能先勾已完成。

個資安維辦法的適用性、5,000 筆／資本額門檻及其計算／過渡規則做法遵欄位，不以單一 users count 或資料庫 row count 假裝完成法定個資筆數判定。內部可先採每年度檢討基線，但不能聲稱未達門檻免除其他安維義務。

### 12.2 Incident workflow

建立 `DETECTED → TRIAGED → CONTAINING → INVESTIGATING → RECOVERING → CLOSED`，各階段可同時開啟通知／通報任務，不等完整調查結束才判斷法定期限。

至少記錄知悉時間、事件類型、受影響系統／租戶、資料分類、推估人數與信心水準、正常營運影響、證據來源、處置、責任人、通報規則、期限、決定及理由、通知／補報歷程、復原與檢討。

- 依實際適用法規與合約建立 deadline rules；安維辦法第 8 條的重大條件與 72 小時規則、現行個資法通知義務及未來新法分開。
- 延遲或分階段通報要記錄理由，資訊不完整不代表可等到最後再處理。
- 若客戶是列管機關或合約要求更短通知，獨立列規則；不把 GDPR 的條件直接套給所有台灣事件。
- 通報與通知內容可產出完整草稿，包含已知事實、不確定項、影響、已做措施與聯絡窗口，不虛構未確認的外洩人數或根因。
- 正式系統可在既有核定應變政策下自動啟動內部告警；開發中的 agent 不自動寄出真實通報或法律聲明。
- 演練包括跨租戶資料外洩、管理員接管、支付 webhook 異常、秘密外洩、備份損壞與 DR 分區；證據封存具 chain of custody、時間來源、hash 與存取限制。

### 12.3 供應商與退出

盤點雲端、OAuth、金流、外送、物流、通知、分析、AI 及外包。每個供應商記錄資料類別、處理角色、地區、次受託、DPA／服務條款版本、事件協助、刪除／返還、可用性與替代方案。

資料中心區域、log／backup 地區與客服支援可接觸的地區各別查核；選台灣／鄰近區域不代表全球人員都不能存取。不因供應商有 ISO 或 SOC 報告，就宣稱自身租戶隔離與法遵已完成。

業務終止與商家停用流程需區分帳戶停權、交易結清、合理資料移轉、法定留存、到期銷毀及證據保存；收費方案停用不能阻擋當事人法定權利。供應商退出後立即停止新分享，歷史資料依合法用途保留。

## 13. CI/CD、雲端設定、備份與 DR

### 13.1 軟體供應鏈及測試隔離

- CI 最小 permission、受信任 workflow、lockfile、套件／漏洞與 secret 掃描、SBOM／license 報告；第三方 action 依風險釘選已驗證版本／commit。
- 不可信 fork／pull request／建置 script 不取得 Production secrets。Preview、staging、production 與 DR 的 DB、Auth、Storage、支付、通知、cron、webhook secrets 必須分開。
- QA 啟動前解析所有可產生副作用的目的地：DB、Supabase URL、Edge、Storage、OAuth project、支付 merchant/environment、Email／SMS／LINE／push、外送與 DR。逐項核對可信環境 identity，不只看 localhost 或 env 名稱。
- 預設合成資料與 mock／sandbox adapter，拒絕任何混入的正式目的地。不得為測試把生產個資複製到本機、Preview 或第三方 AI。
- 外部網路缺失時將整合測試列 BLOCKED，同時完成有意義本機測試。不可使用 mock PASS 充當商用 provider 驗證。
- 如發現已外洩秘密，安全回報其位置與範圍，不輸出值；準備輪替及依既有授權處理。不能只從工作樹刪掉字串就宣稱撤銷完成。

### 13.2 雲端與 DNS

盤點實際使用的 GoDaddy／Cloudflare／Vercel／Supabase，不新增未使用的供應商。查組織擁有權、管理員 MFA、API token 最小權限、dev/prod 分離、分支與發布保護、TLS、CORS、備份、日誌、網域接管及過期憑證。

DNSSEC、CAA、HSTS、網域移轉鎖、origin protection 與 SPF／DKIM／DMARC 依現況提出可回復計畫。郵件先盤點合法寄件來源再提升 DMARC 執行；DNSSEC 需正確协调 registrar／DNS provider，不直接切換破壞解析。

Vercel／Supabase 原始入口可公開可達時，保護設計不能依賴「網址沒人知道」。資料庫 network restriction 對 serverless 連線的可行性要實測，避免盲目限制 IP 導致服務中斷。

### 13.3 備份與復原

列出 DB 資料／角色／schema、Storage 真實檔案、Auth 與憑證、Edge／cron、設定、Secrets 恢復、DNS、Queue／Outbox、audit 封存與部署 artifacts 的恢復方式。**資料庫備份不代表一定包含 Storage 檔案或全部雲端服務設定。**

備份有加密、最小讀取、刪除隔離、保留期限、成功／新鮮度告警與真實還原驗證。PITR／跨區複本能力以實際方案和文件核對。還原到隔離環境，禁用真實支付、通知、外送與印單副作用，再檢查數量、約束、權限與帳務一致性。

RPO／RTO 是需測量的業務目標，先讀現有 SLA；沒有時列草案，不捏造零資料損失或達成時間。確認備份可以還原但未量測端到端，不能寫 DR 已完成。

### 13.4 DR 單一 writer 與切換

- 保留現有 DR-first／migration gate 及 audited cleanup，不因舊規則擋住就刪掉保護。若需修改 gate，先提出與實作精確範圍、證據和回復流程。
- 明確切分 passive replication apply 與本地業務 writer；fence 不阻擋合法複寫，但必須擋本地 seed／backfill／API／cron 產生的非法業務寫入。
- writer 權限由可驗證的 lease／epoch／fencing 或等價機制控制；在 network partition 與舊 Primary 復活時仍能拒絕 stale writer。DNS 切到 DR 不足以停掉舊 writer。
- 找出判斷 writer 的權威與失聯行為；若沒有可靠隔離／仲裁能力，就不提供不安全的自動提升，採先確認舊 writer 被 fence 的受控切換。
- 只啟動一套支付、通知、列印與計費 side-effect worker；接管保留原事件／operation ID。重播事件需防重複外部效果。
- 核對 DB DDL／RLS／functions／grants、table／sequence、Storage／Auth／secret 與 feature flag 的複寫／恢復範圍，不能假定 logical replication 自動包含全部。
- 回切有 reconciliation、衝突處理、刪除 tombstone、session／device／key 撤銷重套與金鑰有效性檢查。不能還原出先前已撤銷的存取能力。
- deployment project ID、environment、domain、release SHA、migration version 和實際資料來源相符；並發 Primary 修改後，回滾／清理只能操作本次確定擁有的資源。

## 14. 法務與商家／顧客條款交付

產出可審查的完整草稿，狀態標 DRAFT，不用假公司資料、假地址／律師姓名或假核定日期。

1. 平台／商家資料角色與責任矩陣：受託與自行決定目的的界線，不能用免責文字推卸法定義務。
2. 隱私告知與政策：實際公司／聯絡資訊待補、目的、資料類別、期間／地區／對象／方式、當事人權利、不提供資料的影響、跨境與委外。
3. 商家 SaaS 服務條款：服務範圍、有效費率與稅金、成功訂單、退款／計費異動、暫停／終止、資料返還與留存、事件協作及責任界線。
4. DPA／委外處理附約：指示與用途、保密、子受託、最低安全控制、權利協助、事故通知、稽核證據、跨境、退出／刪除。
5. 商家個資守則：會員／訂單資料的最小使用、匯出保護、行銷限制、員工權限及離職處理。
6. 顧客交易條款模板與配置：商家資訊、商品／總價／費用、交付、取消／退款、申訴入口、適用解除權及合理例外告知；條款可供查閱與儲存。
7. 食品／生鮮與一般零售規則分開；取消服務、七日解除權、瑕疵擔保及退款不可混成同一條件。食品／商品標示、批號／召回等依實際類別記 legal review。
8. 個資安全維護計畫、业務終止資料處理方法、事件應變與證據保全文件，附可填欄位與 owner；不是只放文件標題。
9. OSS／商標／圖片／字型／外包程式授權清單及疑點。未查契約不自行認定全部程式一定歸某方。
10. 如已有 App：準備資料流與 SDK 對照、帳戶刪除及平台隱私揭露；SaaS 數位功能購買與實體餐飲支付分開審查平台政策，不直接宣稱免 IAP。
11. 如已有 AI：記錄目的與輸入、輸出、保留、provider 及個資邊界；預設不將原始顧客內容用於訓練，不讓模型自行跨租戶檢索、退款、改權或發送。工具呼叫仍需服務端授權。

條款版本與適用交易／方案／同意事件可追溯；不要追溯修改原訂單適用的條款。尚待法律核定的政策可在 staging 預覽，不能標成已核定或已發布。

## 15. 資料模型、設定與遷移要求

先對照既有 schema，以重用與 additive migration 為原則。下列為必要能力，不要求必須使用這些名稱或新增同名 table：

| 能力 | 最少資料／關係 |
|---|---|
| Policy／Legal registry | 類型、版本、生效／核定狀態、來源、適用環境、責任人與覆核時間 |
| Consent／Notice receipt | 租戶、主體、目的／渠道、同意／拒絕／撤回、版本、時間及安全來源 |
| Privacy request | 申請、核對、期限、延長、准駁、執行、法定例外與結果 |
| Retention／Legal hold | 資料類型、起算、期限、理由、範圍、到期、核准及解除 |
| Deletion job／Tombstone | 主體受限引用、資料目標、重試、結果及還原後抑制 |
| Audit／Integrity manifest | 事件、操作、租戶、受限引用、簽章／批次與保存類別 |
| Access review／Support grant | 權限範圍、理由、核准、有效期、撤銷與複核 |
| Device credential | 裝置、門市、權限、版本、hash／加密 reference、到期與輪替 |
| Incident／Evidence | 事件、時間線、影響、deadline rules、決定、證據及存取 |
| Vendor／Data transfer | 服務、角色、用途、地區、次受託、合約與退出 |
| Existing ledger／Inbox／Outbox | 沿用原始交易 ID、冪等、版本、actor、scope 及補償 |

每個新增或變更項目需要：owner、tenant scope、必要 NOT NULL／FK／unique／check、index、RLS／GRANT、runtime role、資料分類、retention、合法刪除、稽核及 migration／rollback 影響。

新增 tenant／加密／policy version 欄位時按 expand → 相容讀寫 → 分批可續跑 backfill → 驗證 → contract。不得重寫已套用 migration、長時間一次鎖全表、在 Production demo seed 或直接把未知 tenant 補成同一租戶。

設定採 schema validation 與環境隔離，使用現有命名方式。至少能表達：管理員 MFA／step-up、支援存取 TTL、敏感匯出保護、retention 模式（dry-run／核定執行）、audit 封存、webhook 與裝置限制、rate limit／成本配額、worker／DR writer mode、正式外部發送開關。

安全預設應是拒絕未授權操作；不得用長期關閉授權 gate 的 feature flag 掩蓋 migration 問題。未準備完成的新功能保持 OFF，既有服務的相容修復按風險逐步發布。

## 17. 必要驗收矩陣

用合成組織 A、B、C，其中 A 有兩個門市；使用 owner／manager／cashier／kitchen／supplier／auditor／支援管理員／匿名／已撤權身分。所有測試在已核對的隔離環境執行。

下列每一項都要對應控制、實際入口、資料庫角色與證據。純模擬 permission helper 不等於實際 API／DB 已驗證。除拒絕結果外，也要驗證沒有寫入、洩漏、重複扣款、匯出或其他副作用；RLS 可能以空結果拒絕，不強求一律 HTTP 403。

| ID | 情境與應驗證結果 |

| T01 | A 使用者以 B 訂單 ID 查詢／修改／取消／重印，被拒絕且不洩漏存在性 |

| T06 | anon／authenticated／實際 Prisma role／worker 分別驗證 GRANT 與 RLS |
| T07 | view、materialized view、SECURITY DEFINER／RPC 不提供旁路 |

| T26 | 條款與告知版本可回查，更新不篡改舊交易與同意事件 |

| T49 | provider 逾時但已扣款，查單／對帳後恢復，不重新扣款 |

| T57 | 印表機跨門市 claim／download／ack 被拒絕，token hash 不供無權者讀取 |

| T59 | 手動開櫃須獨立權限與理由，重印／匿名下單不能開櫃 |
| T60 | POS 斷線／重開／多分頁／同步重送不重單，衝突可處理 |
| T61 | 登出／換店／撤銷裝置不顯示前租戶資料，也不靜默丟棄待同步交易 |
| T62 | App push／deep link／WebView bridge／OS storage 按已存在能力安全運作 |
| T63 | 隔離還原含 DB 與檔案，啟動前沒有真實通知、付款、外送或印單副作用 |

| T65 | DR replication apply 可運作，本地 seed／backfill／cron 不會繞過 fence |

| T69 | 餐飲／生鮮／一般零售退貨、申訴、帳戶刪除與資料移轉流程正常 |
| T70 | 若使用 AI／新增敏感資料：跨租戶檢索、惡意指令與未授權工具副作用被拒絕 |

另保留基本正向閉環：訪客 QR 下單 → 商家接單 → 庫存／優惠驗證 → sandbox 付款或合成現金確認 → 列印模擬 → 正確交付 → PAYG 計量 → 退款／沖銷 → 報表／audit 對帳。Supply Lite 進貨／收貨與既有非庫存服務不得退化。

不寫只重述程式碼的形式測試。先針對控制驗證，再按共享呼叫鏈執行必要回歸；滿足已知風險與要求後停止無目的擴大掃描。型別、lint、build、Vitest／Playwright／pgTAP 等命令從現有 package scripts／CLI help 發現，不杜撰存在的指令。

每份證據包含完整 commit／工作樹識別、指令、環境、工具版本、exit code、assertion／scenario、時間與安全 log 路徑；使用 dirty worktree 測試時明確留 tree／diff 身分，不能假裝只是已提交 HEAD。產物不得含秘密或真實顧客資料。

## 19. 外部設定集中到最後

每項設定列：用途、受影響控制、指定環境／資源、現況、建議精確變更、所需權限、是否增加費用、影響、驗證、復原、owner、完成狀態。不要要求使用者將 secret 貼進聊天或提交到 git。

至少檢查：

- 公司／商家法定資料、實際聯絡窗口、業務類別、資料角色、服務條款、DPA、保存政策與律師／會計核對。
- Google／LINE／Apple 的正式／測試 client、scope、redirect、憑證、帳號連結、MFA 與恢復配置。
- 雲端組織與 project 身分、MFA、最小 token、Preview 隔離、DB role／RLS、Storage policy、Realtime 及 Edge 保護。
- 支付商戶資格、每個 provider 的 sandbox／production 帳戶、webhook、憑證輪替與退款／對帳實測。
- foodpanda／Uber Eats／物流／通知／電子發票各自規格、商用授權、受託與資料使用安排。
- 長期必要稽核封存與獨立管理能力、簽章／金鑰、期限及實際保存成本。
- 備份／Storage 恢復／PITR／DR topology、writer fence、切換權限、演練時段與已核定 SLA。
- WAF／origin、DNS、DNSSEC／CAA／TLS、寄件驗證與告警渠道。
- Star／iPad／Bluetooth／webPRNT／CloudPRNT 的實機授權、門市網段、裝置憑證與開錢櫃驗證。
- App 商店帳號、隱私揭露、SDK／權限、帳戶刪除與實際上架政策；僅對已存在／本次適用的 App 處理。

缺法律核定、費用或人工設定時，先完成具體可審查內容。取得資料後提供可重新執行的 preflight／驗證流程；不能讓「全部集中最後」變成最後無法說明到底要設定什麼。

## 20. 發布門檻、復原與最終回覆

1. 已確認的跨租戶外洩、授權旁路、秘密洩漏、支付重複副作用、DR 雙寫與必要證據缺失，列相關功能發布阻擋項，不以一般風險接受勾選掩蓋。
2. 未測硬體／正式 provider／法務文件等清楚列 BLOCKED；程式可完成並預設關閉新功能。不得把整個專案所有低風險改善都綁成同一次大上線。
3. 依授權做本機／staging 驗證與小範圍 rollout 計畫。正式變更要有指定環境、差異、備份／復原、gate、觀測與回復條件；已授權的操作不重複要求確認。
4. 回復不得依賴刪除新交易或回滾所有 schema；先定義 feature rollback、相容讀寫、資料補償與不可逆步驟。必要 security fix 不能藉 rollback 重新打開已知漏洞。
5. 若既有遠端協作授權允許，可整理分支與 Draft PR 供審查；不自行合併、正式啟用收費或發出法律声明。

最終回覆請包含：已改了什麼／解決何種風險；實際测試結果與證據；仍存在風險；程式、環境、法務及發布各自狀態；最後需要一次處理的具體清單。不要只回覆「已全面完成、符合個資法、通過資安」。

## 21. 參考技術來源及執行時更新

- [Supabase Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security)：確認 exposed schema、GRANT、JWT、view、service role 與實際角色行為。
- [PostgreSQL Row Security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)：核對 table owner、BYPASSRLS、policy 組合與目前使用版本。
- [Supabase Changelog](https://supabase.com/changelog)：按本次實際 SDK／DB／平台版本核對 breaking change，不把最新版本直接灌入既有專案。
- [OWASP ASVS](https://owasp.org/www-project-application-security-verification-standard/)：使用正式發布版本及正確 requirement identifiers。
- [NIST CSF 2.0](https://csrc.nist.gov/pubs/cswp/29/the-nist-cybersecurity-framework-csf-20/final)：治理與風險溝通基準。
- [PCI DSS](https://www.pcisecuritystandards.org/standards/pci-dss/)：按支付接觸範圍與收單契約確認。
- [Apple App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)：有 App 時核對隱私、刪除、SDK 與支付分類。
