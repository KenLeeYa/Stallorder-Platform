# Personal notification Inbox

Local B4a implementation; independent review and runtime acceptance are recorded separately in `.superpowers/sdd/2026-10-01-awesome-optimization/batch-4a-report.md`. No provider, physical-device or release success is implied.

The Inbox projects existing facts. It creates no notification queue or delivery scheduler. `BILLING` uses BillingNotification in an explicit organization with current VIEW_BILLING permission; `APPLICATION` uses the current applicant's MerchantApplicationNotification or a platform administrator's explicit application case; `STAFF_ORDER` requires an actual StaffPushDelivery whose Subscription belongs to the current profile and stall, plus current VIEW_ORDERS permission. Multiple device deliveries for one order produce one row per person. An order alone is not a notification. Disabled subscriptions retain history; deleted underlying sources cascade their read receipts.

`src/lib/notification-inbox-contract.ts` is the pure strict v1 DTO contract. `src/server/notifications/inbox-service.ts` revalidates current session/profile/version and permissions on every operation. The cookie-only Web routes are GET `/api/notifications`, `/api/notifications/unread-count`, `/api/notifications/[source]/[id]`, PATCH `/api/notifications/[source]/[id]/read`, and GET/PATCH `/api/notification-preferences`. Scope query fields match the discriminated DTO (`PERSONAL`, `ORGANIZATION`, `ADMIN_APPLICATION`, `STALL`). Unknown/duplicate fields are rejected. Writes require CSRF, all responses are private/no-store, errors contain safe codes and request IDs. Native bearer transport belongs to later work.

The list has a default 30-day window, maximum 90 days, 20 rows by default and at most 50. Each explicit scope selects one source, ordered by createdAt descending then UUID descending. Signed cursors bind the current profile, scope and filters; HMAC uses existing TOKEN_DERIVATION_SECRET with a separate purpose string. Missing signing material fails closed when pagination is needed. No new credential is provisioned. The same visibility/category/date predicates determine unread counts. The date controls explicitly use UTC, inclusive start and exclusive end.

Read receipts are per profile, with source-specific foreign keys and an exclusive source check. Staff receipts use a composite delivery/order FK and profile/order unique key. Read is explicit and idempotent. Provider acceptance/display does not imply read. Applicant reads mirror their own legacy readAt; administrator reads never mark the applicant read. Shared legacy billing readAt does not manufacture personal receipts. Only old applicant recipient readAt values are backfilled.

Preferences use a required positive version, profile-row lock and compare-and-swap conflict409. Default visibility is true; analyticsConsent is independently false. Visibility affects only Inbox and count, not delivery subscriptions, marketing consent or telemetry. No analytics collector is added. Both new tables force RLS, deny PUBLIC/anon/authenticated and grant service_role only SELECT/INSERT/UPDATE; existing backend-writable guards remain mandatory.

Merchant dashboard and billing, applicant status, platform case and staff pages expose native Inbox links. The dashboard entry uses the current authorized workspace and the same VIEW_BILLING guard; it does not change existing dashboard entitlement gates or enable the billing feature flag. Feature-on billing UI verification remains NOT_RUN_FEATURE_DISABLED in this local fixture. The mounted panel supports filters, pagination, detail, explicit read and versioned preferences. Controls are disabled until handlers are ready. Current identity/scope changes remount private state; authorization denial or existing private-view invalidation aborts pending requests and unmounts private contents without touching pending POS/offline data. Deep links are allowlisted native paths whose existing destination authorizes again.

`e2e/responsive-lab/awesome-batch4a-inbox.spec.ts` exercises actual Web flows. Its test-only helper `scripts/awesome-optimization/batch-4a/mock-staff-push.mts` checks frozen build/local schema/corpus before constructing fixtures, creates two owned encrypted subscriptions and an actual authorized order, then runs the original global worker only if every eligible delivery is owned. An ephemeral fixed loopback HTTP fixture returns418 through the exact web-push send seam. Canonical result is FAILED/PUSH_HTTP_418 and the separate receipt is SIMULATED_REJECTION. It is not accepted Push, genuine provider delivery or physical display. Production worker/config/producer/status CHECK are unchanged. Existing facts are compared before/after; arbitrary HTTP(S) calls during the seam are rejected. Socket, facade and synthetic environment are restored in finally.

`scripts/awesome-optimization/batch-4a/database-constraints.mjs` verifies actual SQL role and constraint denials in rolled-back transactions. The new named schema overlay preserves the original fixed201 application projection; prior overlay/freeze and two approval facts remain authoritative. Final evidence includes raw failures, source/build identities, fresh preimages and immutable receipts. B4b report execution, B4c LINE/Webhook, native app transport and telemetry remain separate later tasks.
