## Isolated capability qualification

`delivery-credential-preview.yml` is a manual owner/main-only entry on an ordinary GitHub-hosted runner, using the existing protected Preview environment and shared PR389 writer lock. Main and staging trees must agree. It accepts only the first attempt of a run and has no inputs selecting a project, role, SQL or credential.

The module binds the existing data-less PR389 project `teunnvfakbfzmodajqjz`, verifies its actual pooler, and refuses to issue a role if any CLI login role already exists. It records a non-secret intent, makes one role-issuance request, retains the returned secret only in process memory, and uses a fixed read-only native query to record actual current/session identities and RLS-bypass state. The native client inherits only fixed libpq fields and PATH; it does not receive provider tokens.

A strictly validated returned role qualifies for one managed cleanup request only when a fresh inventory contains exactly that role, including after native or credential-shape failure. The fixed Preview `DELETE /cli/login-role` endpoint deletes all CLI roles, so both the initial empty inventory and the pre-delete exact singleton are required. Readback must confirm an empty inventory. A scope mismatch or any cleanup request failure keeps the result failed even if a later read returns empty. An unknown issuance outcome, invalid role name, cancellation, or failed cleanup blocks continuation; it is never retried or guessed into a cleanup target. A cancelled job may require reconciliation from the original non-secret intent/issued receipt before another run.

This managed cleanup relies on one writer for the whole operation, including local CLI, Dashboard and other provider callers. The shared GitHub lock serializes repository workflows; it cannot lock outside actors. The provider endpoint has no per-role conditional deletion, so the inventory checks do not establish atomic deletion or eliminate TOCTOU. This procedure is confined to the existing isolated Preview and cannot be reused for Primary, which already has an older CLI role.

The result always retains `rotationQualified: false` and `releaseAuthorized: false`. No Primary write, password reset, Vercel action, privilege grant, reusable credential export, new project/branch or paid provider call is implemented by this workflow. Actual application compatibility and a sufficiently durable recovery window remain separate requirements.

## Managed-role cleanup correction before issuance

The pre-execution review found an Important issue in the original cleanup design. PostgreSQL 17 requires a non-superuser to have both CREATEROLE and ADMIN OPTION for the target role before DROP ROLE. Supabase documents that CLI roles belong to supabase_admin and cannot be dropped through ordinary postgres SQL. The old synthetic cleanup fixture incorrectly accepted that SQL. No hosted credential probe or issuance was performed before this finding. See the [Supabase CLI-role cleanup explanation](https://supabase.com/kb/troubleshooting/permission-denied-when-deleting-the-cli_login_postgres-role-808bae) and [managed deletion endpoint](https://supabase.com/docs/reference/api/v1-delete-login-roles).
